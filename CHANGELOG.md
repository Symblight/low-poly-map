# Changelog

All notable changes to the SimWorld library (Rust `WorldStreamer` GDExtension plus the Godot-side runtime) and its `WorldStreamer` contract. Versions follow semver. `api_version` (from P2) is the contract major.minor, independent of the crate version, and is listed per release; the contract itself is `docs/contract.md`.

Format: one section per release, newest first. Every contract change (a method, a dictionary key, an encoding, a guarantee) must be listed here, in `docs/contract.md` and in `api_version` (`API_MAJOR`/`API_MINOR`), in the same commit.

## Unreleased

- **Material prewarm starts when a camera exists (Godot addon only, no contract change).** `WorldView` started the prewarm only if a camera was known at `Start()`; a host whose cameras enter the tree after the view (SimPlane: the view starts inside the world node's `_Ready`, the cameras are later siblings) got none, and the first tile draw plus the first dither fade compiled every world shader and pipeline inside a frame: one 4.7 s frame on Metal Forward+ (SimPlane bug report of 2026-10-29, `frame_max_ms` 4730, `cpu_process_max_ms` 4719), 7 s between the first two frames in a scripted run. Now `StartPrewarmIfReady` runs at `Start()` and on every frame until `ViewCamera` is non-null; the same host then shows a worst frame of 146 ms during the 24 prewarm frames and nothing above 17 ms afterwards.
- **`CameraSwitchSource` takes a travel-velocity provider (Godot addon only, no contract change).** The cover looks ahead by velocity x `bands.look_ahead_s` (20 s, clamped per band), and a chase camera swinging on its arm reported that swing as velocity: in SimPlane a right-drag of the chase camera gave 136 m/s and 812 deliveries + 475 unloads in 5 s with the aircraft parked, i.e. the whole streamed set moved and faded on every swing ("everything is blinking when I move the camera"). `CameraSwitchSource(current, all, velocity)` now takes the vehicle's velocity (SimPlane passes the aircraft node's); the same drag then streams 0 tiles. Without a provider the camera's own motion is used as before.
- **One error when the origin shifts on three consecutive frames (Godot addon only, no contract change).** A host that does not move its vehicle and cameras by the shift (contract section 2) is beyond `origin.recenter_distance_m` again on the next frame, so the origin moves every frame and the whole world jumps back and forth (SimPlane, 2026-10-29: 5 km per frame at 120 Hz, 184 shifts in 5 s, the streamed set collapsing to 19 tiles). `WorldView` now pushes one error naming the cause and the two ways out (apply the shift, or raise `origin.recenter_distance_m`).

## 0.5.0 (2026-10-29)

Contract `api_version` 1.11, profile_version 7, crate 0.5.0. The first version SimPlane vendors (`docs/spec-simplane-integration.md`); the library is under a feature freeze until the game flies over the seed world (`docs/decision-library-direction.md`). Verified on this release: the Rust suite, the bench self-tests under both Mobile and Forward+ (Metal), the pixel-level hole check, the seed self-test, and a fresh Godot 4.7.2 .NET project in SimPlane's configuration loading the built addon. macOS arm64 libraries only; Windows, Linux and iOS are unbuilt. Known Godot 4.7.2 quirk found by the fresh-project check (not a library bug, reproduced with another GDExtension): the first headless `--import` of a project with any GDExtension completes the import and then crashes at exit (code 134); the second import exits 0 (`docs/spec-simplane-integration.md` L5).

- **Pre-integration pass for SimPlane (`docs/spec-simplane-integration.md` L1-L7; Godot addon and repo only, no contract change).** `NightLook.ApplyFog` (default true): off, `ApplyStatic` / `Update` never touch a fog property, for a host whose weather system writes the environment's fog (SimPlane's `SkyController` uses exponential fog from visibility; the night look's depth fog overwrote it). `CameraSwitchSource(Func<Camera3D?> current, IReadOnlyList<Camera3D>? all)` for a host that switches cameras (chase / cockpit): the pose, the velocity (zero on the frame of a switch) and the view come from the current camera; new small interfaces `IWorldCameraTick` (the view ticks the source once per frame; `Camera3DSource` implements it, the view no longer ticks only its own adapter) and `IWorldCameraProvider` (`CurrentCamera`); `WorldView.ViewCamera` = the provider's camera or the `Camera` export, used for set_view, the sprite pixel scale, the far plane and the material prewarm, so the `Camera` export may stay empty with such a source. Every addon `.cs` file starts with `#nullable enable`, so the addon compiles unchanged in a host project with `<Nullable>disable</Nullable>` (SimPlane). `LICENSE`: MIT. Contract 9 "Airports": one sentence for physics hosts (wheel contact = `ground_height_at`, plus 3 x `ground.rN.lift_step_m` inside a runway strip). Repo: the 19 merged side branches and the 12 agent worktrees removed, `.claude/worktrees/` ignored.
- **Engine surfaces: meshes packed in Godot's vertex layout on the workers (perf review 3 item 1; additive, api 1.11; contract 3.1, 4, new section 4a).** New `configure_world` option `engine_surfaces` (bool, default false: nothing changes for the current host). With it every building, ground and terrain mesh comes as a Dictionary in the exact shape of `RenderingServer.mesh_add_surface` / `ArrayMesh._surfaces` (`mesh_surface`, `ground_surface`, `terrain_surface`; the `mesh` / `ground` / `terrain` Arrays are then empty and the library holds the packed form only): `format` (Godot 4 uncompressed format version 2), `vertex_data` (positions f32, then octahedral normal + generated tangent u16), `attribute_data` (COLOR RGBA8, TEX_UV f32), `index_data` (u16 up to 65536 vertices, else u32), `vertex_count`, `index_count`, `aabb`, `primitive`. New `surface.rs` (encoder, sourced from Godot 4.7.2 `rendering_server.cpp` `_surface_set_data` / `mesh_surface_make_offsets_from_format` / `mesh_create_surface_data_from_arrays`), `mesh_data.rs` (`MeshData` moved out of `mesher.rs`, 1777 -> 1728 lines, with `pack_engine_surface`; counts answer for either form), `worker/surfaces.rs` (packing at the end of each tile job). Verified: `surface_tests.rs` decodes the bytes back (positions, UVs, indices exact, colors to 8 bits, normals within octahedral precision, tangents orthogonal) for every band and both terrain shadings and a > 65536-vertex mesh, and a world with the option delivers exactly the packing of what a world without it delivers; in Godot 4.7.2 (headless, two synthetic worlds with terrain) the library's bytes equal `RenderingServer.mesh_get_surface` of `AddSurfaceFromArrays` for all 1278 meshes (1.1 M vertices: format, vertex, normal / tangent, attribute and index bytes, AABB identical), and `ArrayMesh._surfaces` reads back the same arrays. Cost: worker packing per tile on vilnius-v2 (`perf_surface_encode`, release, thread CPU, best of 3): R0 0.084 ms (4976 vertices, 5 % of the chunk build), R1 0.232 ms (13 504 vertices, 7 %), R2 0.242 ms (14 093, 5 %), R3 0.026 ms, terrain 0.002 ms; main thread in that Godot check 0.035 -> 0.005 ms per mesh on average (synthetic, 860 vertices per mesh; the dummy renderer skips the GPU upload). The host side (C#) is a later step.
- **CPU time in every `diagnostics.profile` line; `poll_fades`, `poll_unload`, `debug_stats`, `lod_state` profiled (perf review 3 item 4; additive, api 1.11; contract 3.1 `diagnostics`).** New `world/call_profile.rs` (`CallTimer`, `World::call_timer` / `end_call` / `end_call_with`): a call slower than 1 ms of wall time logs `WorldStreamer profile: <call> <wall>us wall, <cpu>us thread CPU [breakdown]`; `update_camera` and `poll_ready` moved onto it (their lines gain the thread CPU; `world.rs` 10 lines shorter), the binding wraps `poll_fades`, `poll_unload`, `debug_stats` and `lod_state` including the conversion to Godot types. Wall far above CPU = preempted or waiting, CPU close to wall = work in the call. From the Rust side none of the four can block: `drain_fades` / `drain_unload` move keys out of `Vec`s the scheduler filled (no lock, no channel, no free of tile data: tile outputs are released on the pool, `Worker::release`); `debug_stats` takes the job pool's mutex once (`JobPool::stats`, a few counters; workers hold it only to pop / finish a job, never while running one) and reads atomics. A 10-30 ms stall on these calls is therefore preemption of the main thread or Godot / .NET work around the call (Variant and Dictionary allocation, marshalling, GC). No allocator switch: nothing measured points at malloc contention (mimalloc would be a dependency for iOS too; revisit only with a profile line showing CPU time inside these calls).
- **Far street lamps: per-band spacing (perf review 3 item 3; additive, api 1.11, profile_version 7 unreleased, so no bump; contract 3.2, 8; intended output change).** New profile key `lights.street.spacing_scale` (4 numbers 1..16 by band, default `[1, 1, 1, 2]`): band N places a lamp every `spacing_m x spacing_scale[N]`, and such a lamp stands for `k = spacing_scale[N]` lamps, a = `intensity(k)` = sqrt(k) / 8 (0.177 at R3), so the host can restore the energy with `count = (8 a)^2`; clusters sum the counts of their lamps (`lights::lamp_count`). Street lamp code moved to `lights/street.rs` (`lights.rs` 559 -> 471 lines). Measured on vilnius-v2 (`perf_stream_far_street_lamps`, the 144 R3 chunks of the 9 overview tiles around the origin): R3 street sprites 24887 -> 12380 (standing for 24760 lamps), per chunk mean 173 -> 86, max 941 -> 459; R2 unchanged (default scale 1; at 2.5 km a 35 m spacing is 13 px, so thinning would show). Golden hashes: only the two R3 tiles changed, in `GOLDEN` and `GOLDEN_TERRAIN` (street lights of R3 only). Host: draw a street sprite with a > 0.125 at `count` times the single-lamp brightness to keep the far carpet as before.
- **Recent-tile cache and the waiting terrain plan (perf review 3 item 2; no behaviour change, no contract change).** `scheduler/recent.rs` keeps its entries in two age-ordered sets (held by delivery time, departed by departure time) next to the map: an eviction takes the oldest entry in O(log n) instead of a `min_by_key` scan of the whole map per evicted entry, and `expire` only looks at the oldest departure instead of walking every entry each frame (`ordered_eviction_matches_the_scan_policy` pins the same policy against the old scan on 20 000 random operations). Measured (`perf_recent_cache_frame_cost`, release, 1200 entries, one eviction + one departure + expire per frame): 8.57 -> 0.54 us per frame. A terrain plan that waited on a box probe (async boxes) is now reused until the next probe batch arrives (`BoxRequests::generation`, `PlanMemo::still_valid(.., probe_gen, ..)`), with the same slack rules as a complete plan; `a_waiting_plan_is_reused_until_a_probe_arrives` holds probe answers back 4 frames, checks every reuse against a fresh plan, the host rule every frame and that the cover settles to the inline one. In the real-archive flight 14 % of the frames start with a probe pending (1003 of 7200). New harness `perf_flight_tests.rs` (`perf_flight_long`: 250 m/s, 300 m, terrain + landmarks, 5 minutes, `update_camera` CPU / wall p50 / p99 / max per minute). A / B on the shared machine (base, new, base, new; whole 300 s, thread CPU): p99 1.76 / 1.43 / 1.85 / 2.11 ms, max 2.30 / 2.33 / 2.80 / 4.52 ms; the minute windows swing by 2x between runs of the same binary (p50 0.35 -> 1.46 ms with E-core scheduling), so the flight shows no measurable difference: a `sample` of the main thread puts the recent cache at 1-2 of ~300 `update_camera` samples and the terrain plan at about 3 %; the cost is the vector cover walk inside `Scheduler::update` (not growing with run length in these runs). Not reproduced: the audit's growth from 0.39 to 0.87 ms p99 at 60 s.
- **Whole tiles blank for up to 0.75 s at the start of every refine swap (Godot addon only; contract section 6 clarified, no api change).** Reported by the user as "sometimes when I move the camera a tile-shaped hole shows the flat terrain; the overlay says consistent", found by `--hole-check` with the pixel test (`--hole-pixels`: magenta background, terrain and fallback off, single-frame spikes). At the start of a refine the library lists the outgoing parent at exactly 1.0 and its 4 children at 0.0 (`scheduler/tests.rs` `refine_fade_keeps_parent_until_complete` pins it), and keeps the parent at 1.0 until the distance-driven fade has moved by half a quantum: one frame while approaching, but until `fades.cap_s` (0.75 s) when the camera hovers, turns or recedes. `WorldView.PollFades` read every 1.0 as "transition finished" and ended the parent's transition: with all 4 children uploaded the visibility rule then hid it (`HiddenByChildren`) while the children, at fade 0, drew nothing. `PollFades` now keeps a tile with an entry visible at 1.0 (dither off, entry dropped on the first call without it), as the contract's visibility rule says. Measured on the same seeded flight (pixel test, vilnius-v2, 150 s): 22 frames with a missing tile (worst 412 solid 4x4 blocks) and 20 quick toggles before, 0 and 2 after. This also explains the "quick toggles" (a parent hidden at the swap start, shown again a few frames later).
- **Collector pacer hardened before the game turns it on (Godot addon only, no contract change).** `GcPacer` is one per process (`Acquire` / `Release`, ticked once per process frame; two `WorldView`s used to run two pacers against the one runtime region), a refused `TryStartNoGCRegion` backs off 10 s instead of retrying every frame (a refused start may itself run a full blocking collection), `NOTIFICATION_OS_MEMORY_WARNING` ends the region, collects and holds the pacer 60 s, `RotateNow()` lets the game rotate at a quiet moment, the rotation no longer runs an extra `Collect(0)` (the start runs the full collection itself), and the last view's `_ExitTree` ends the region with a collection and `WaitForPendingFinalizers` (ending it bare aborted the quit with `mutex lock failed`: the finalizer thread reached the engine during teardown). `PointSurface` (the points-mesh engine surface of the R0 / R1 tiles and the sprite cells) is an instance per owner that reuses its dictionary and disposes the two byte `Variant`s at once, as `MeshSurfaces` does; before, every call left a dictionary, an array and two finalizable wrappers holding about 186 KB of native bytes until the next collection, which a paced collector puts off for minutes. Bench: the baseline key carries `@gcq<MB>` when the pacer ran. Default stays 0 (off), the addon never enables it. Measured afterwards in a 600 s soak (`low-250`, release): 64 MB gives 5 rotations instead of 30 collections, but one rotation paused 184 ms (283 k objects pending finalization), the managed heap grew from 38 to 226 MB across rotations and the frame p50 doubled by the end of the run, and 16 MB was no better (23 rotations, worst 224 ms, heap 39 to 261 MB, the same halved frame rate at the end), so the pacer is not recommended; the per-frame finalizable objects (the three poll wrappers, the light arrays) are the cause and the thing to cut.
- **Tile-shaped holes / black light sprites after a long flight: no more instance uniforms (Godot addon only, no contract change).** The dither fades kept their per-tile values (`fade`, `fade_parity`, `fade_mul`) in shader `instance uniform`s. Godot reserves 16 entries of one shared buffer for every node that is ever given a material declaring one (`rendering/limits/global_shader_variables/buffer_size`, default 65536 = **4096 nodes in the whole project**), on assigning the material, not on setting a value; the entries come back only when the node is freed, and a node without a slot logs `Too many instances using shader instance variables` and reads every instance uniform as **0**, not as its declared default (measured in a 20-line test project: 904 of 5000 nodes read 0). The sprite shaders declared `fade_mul` always, so each pooled tile set took 5 slots on creation, plus 2 for the first fade of its building and ground nodes; a pool of ~900 sets plus the terrain pool passed 4096 within a minute of flying. A faded tile of a set without slots drew no pixel for the whole swap (ground and buildings of one tile or one quarter gone, the terrain layer showing through, `cover consistent` as ever) and its sprites were black. Now `FadeMaterials` (new) rents a clone of the dither variant per fading node (plain uniforms; `Duplicate()` of the configured template, later parameter changes go through `FadeMaterials.Set` to the template and every clone), the sprite shaders have a `LOD_DITHER` variant like the mesh shaders (plain materials: `const fade_mul = 1.0`), `lod_dither.gdshaderinc` uses plain uniforms. No instance uniform remains in the addon and no project setting is needed; at most `fades.max_active` x 5 tiles fade at once, so ~20 clones per node kind exist. Bench: `--hole-check`, `--hole-flight`, `--fade-selftest`.
- **Rust performance (within api 1.11, unreleased; no behaviour change unless noted).** Measured with `simworld-core/src/perf_tests.rs` (ignored, release: `cargo test --release -p simworld-core perf_ -- --ignored --nocapture --test-threads=1`): synthetic city, 250 m/s at 300 m AGL, 60 Hz real time, `update_camera` wall and thread-CPU percentiles flat vs terrain, the CPU of the other threads, idle CPU, synthetic cold fill, job-pool overhead.
  - **`update_camera` with the terrain layer (perf review item 1).** The terrain split plan (`scheduler/terrain_plan.rs`) records the slack of every threshold decision (`scheduler/plan_memo.rs`) and a later frame reuses it while a bound on how far any compared distance or horizon line can have moved is below that slack, the roots / SSE scale / guard are unchanged, the budget did not bind and the nodes inside the hysteresis band kept their state: then the plan is provably the one a fresh run gives (the cover stays pure; `plan_memo_tests::plan_reuse_equals_a_fresh_plan` recomputes every reused plan in a flight with climb, turn, hover, detail and fov changes, plain and seed world; about 80 % of flight frames reuse). The tile-box memo of the scheduler and the `ErrorProxy` memo evict gradually (`gen_cache::GenCache`, two generations) instead of being wiped when full, so a long flight no longer recomputes every box in one frame. The look-ahead view points are projected and sampled once per distinct point (`scheduler/view.rs`; was twice per band for all 9 slots). Decoded data tiles the store drops (idle or budget eviction) are freed on a pool thread (`Worker::release`, `worker/release.rs`, one lowest-priority job per frame) instead of inside `update_camera`, where a tile's thousands of allocations cost 1-4 ms in single frames, flat and terrain alike. Measured (`perf_update_camera_flat_vs_terrain`, 40 s flights, base and new binaries interleaved twice on the same loaded machine; thread CPU of `update_camera`, ms): flat p50 0.44 -> 0.42, p95 0.74 -> 0.69, max 3.5 / 7.7 -> 1.0 / 1.1; terrain p50 0.92 -> 0.74, p95 1.45 -> 1.22, max 5.1 / 6.2 -> 2.6 / 2.7 (frames over 3 ms 3 -> 0; the slowest is now the first moving frame, when the look-ahead jumps from 0 to 250 m/s); terrain p95 / flat p95 1.96 -> 1.77. On an idle machine the same harness gave flat p50 0.16 / p95 0.23 ms and terrain p50 0.30-0.35 / p95 0.5-0.8 ms; wall times include preemption by other processes.
  - **Idle job threads block (perf review item 2).** The job pool's 100 us `yield_now` poll after each job is gone (`PoolConfig::idle_spin`, `DEFAULT_IDLE_SPIN` removed): an idle worker waits on the condition variable at once. `perf_job_pool_trickle` (4 threads, 6 jobs of 20 us per 60 Hz frame): pool CPU beyond the jobs' own work 0.32 -> 0.05 ms per frame.
  - **Raised-part stacking without the quadratic scan (perf review item 3).** `mvt::stack_raised_parts` (moved to `mvt/stack.rs`) puts the grounded footprints into a uniform grid of their bounding boxes once more than 4 raised parts are in a tile and tests only the footprints whose box holds a part's centroid (a few raised parts keep the direct scan, cheaper than the grid). Same candidates in the same order: bit-identical bases (`mvt::stack::tests::bucketed_stacking_equals_the_plain_scan` against the old scan, goldens unchanged). Densest real tile 14/9342/5207 of `vilnius-v2.pmtiles` (1586 buildings, 1 raised part; the most raised x grounded in the Vilnius area): 0.021 ms before and after; the same tile with a raised part on every building (3172 buildings, 1587 raised): 29.4 -> 0.28 ms (`real_archive_densest_tile_stacking_timing`, ignored, release).
  - **Synthetic overview tiles leave the block bases to the chunks (perf review item 4).** A synthetic z11 overview tile has thousands of street blocks and each block base samples the terrain about a hundred times; with the terrain on that was 106 ms of the tile's job, run for every overview tile in the 25 km reach although only R2 chunks mesh blocks (R3 draws light points). The tile now leaves them open (`DataTile::lazy_bases`, `data/bases.rs`: one `OnceLock` per block) and the R2 chunk jobs resolve the blocks they mesh, in parallel, each once, with the same function and projector (bit-identical; every golden unchanged). Overview tile at the origin with terrain: 106 -> 24.6 ms (`perf_synthetic_overview_tile`). Synthetic cold fill with the terrain layer (`perf_synthetic_cold_fill`, same machine, interleaved runs): 2.81 / 2.86 s -> 2.48 / 2.48 s wall, 9.9 -> 8.3 s process CPU; flat unchanged (0.13 s). `synthetic_data_tile` / `synthetic_chunk` moved to `data/synthetic.rs`.
  - **`lod_state()` (perf review item 5; additive `#[func]` within api 1.11, unreleased; contract sections 1 and 3).** The host reads the live LOD state 4 times a second; `debug_stats()` builds every overlay counter (stats, memory, latency tables) for that. `lod_state() -> Dictionary` returns only `tau_eff`, `lod_quality`, `lod_edges_m`, `lod_tiles_est`, `lod_max_tiles`, `view_fov_y_deg`, `view_height_px` (same values as the `debug_stats` keys, which now come from the same `World::lod_state()`, one capped-quality bisection instead of three) plus `terrain_active`, `terrain_tau_eff` (`terrain.tau_px` x the `set_terrain_detail` scale) and `terrain_detail`, every key always present. `simworld_core::world::lod::LodState`; test `world::lod::tests::lod_state_matches_the_getters`; `#[func]` count 23 -> 24.

- **Rust performance, round 2 (perf review 2; within api 1.11, unreleased).** Measured with `simworld-core/src/perf_stream_tests.rs` (ignored, release: `cargo test --release -p simworld-core perf_stream -- --ignored --nocapture --test-threads=1`, with `SIMWORLD_V2_ARCHIVE=<vilnius-v2.pmtiles>` on the real two-level archive through an in-process range server, terrain on, landmarks on): first `update_camera` after `configure_world`, the settle at 300 m, then 250 m/s level flight at 300 m (60 Hz real time): `update_camera` wall and thread-CPU time, `pop_ready` per tile, keys delivered again within 10 s of their unload; `perf_stream_cold_fill` adds the first-delivery latency table. Numbers below are A/B runs of the same harness on the same (busy, shared) M2 Pro, alternating old and new builds; CPU times are the robust ones there.
  - **Cold tile boxes off the main thread (item 1; contract sections 5 and 11 clarified, no api change).** The terrain [min, max] under a tile and the terrain cover's error proxy come from the tile's 9 x 9 probe (81 height evaluations, ~0.1 ms); the first frame after a configure needed some 200 of them for the vector roots (z13 within 25 km) and the terrain plan, all on the main thread. The world's schedulers now run in async-box mode (`scheduler/boxes.rs`): a miss is requested instead, the requests go to the CPU pool as top-priority probe jobs (`worker/probe.rs`, 12 keys per job), the next `update` takes the probes in (boxes into the memo, error proxies parents first). Until a value is known the cover waits for it and never guesses: a root candidate without a box is not added, a node starts no split until its 4 children's boxes (terrain: and its own error proxy) are known (asked for ahead within 1.5 x the refine distance, so a split in flight is not held up), and what is in the cover keeps its state; a terrain plan that met a missing value is not reused. Once known, every value is bit-identical to the inline one (one probe function, `terrain::sample::probe`, now also behind `Terrain::tile_range` and `ErrorProxy::probe`), so the settled cover is the same: `scheduler::boxes::tests::async_boxes_settle_to_the_inline_cover` (vector layer with terrain and terrain layer: settle, a 250 m/s flight with the host rule checked every frame, settle again; equal to the inline scheduler), `first_update_probes_nothing_inline`. Schedulers built directly (tests, tools, goldens) probe inline as before; every golden unchanged. `settled()` also waits for outstanding probes. v2 archive, terrain on: first `update_camera` 22.2 / 25.8 / 27.9 / 23.0 ms CPU -> 0.13 / 0.13 / 0.15 / 0.09 ms; worst flight frame 2.85 / 2.81 / 2.66 / 2.76 ms CPU -> 2.45 / 1.64 / 2.46 / 1.73 ms (no frame over 3 ms in either); p50 unchanged (0.36-0.40 vs 0.37-0.41 ms); worst settle frame 0.9-1.2 ms both.

  - **Worker threads from the profile (item 2; new key `streaming.worker_threads`, profile_version 7, unreleased, so no bump; contract section 3.2).** The CPU job pool had cores - 2 threads clamped to 2..4: 4 of a 10-core M2 Pro, while R2 / R3 chunks waited up to 1.9 s for a build slot (`mesh_wait`). `streaming.worker_threads` (0..64, default 0 = automatic: cores - 2, at least 2, at most 8; `jobs::worker_threads`, `jobs::auto_threads`); a mobile host sets its own. `perf_stream_cold_fill` (v2 archive, terrain on, 8 s at 300 m over the origin, one binary, 4 threads vs automatic = 8, 3 rounds each): `mesh_wait` p50 / p95 R1 160-181 / 239-264 ms -> 112-122 / 172-199 ms, R3 920-960 / 1042-1064 ms -> 718-737 / 823-841 ms; last delivery per band 20-110 ms earlier (R3 7577-7651 -> 7529-7599 ms: the fill is bound by the host's 2 tiles per frame, `deliver` dominates `total`); the first tile of each band came 20-40 ms later (8 jobs share the cores with the terrain builds; on the busy test machine).
  - **Coarse terrain tiles from a 128-cell height patch, and a stoppable TIN build (item 3; new key `terrain.bands[].patch_cells`, profile_version 7, no bump; contract sections 3.2 and 9a; intended terrain mesh change).** A T2..T4 tile (z12..z10) sampled 257 x 257 heights (6 octaves, ridges, plateaus, valleys: ~80 % of its build) to make ~800 triangles. The band's height grid is now `terrain.bands[].patch_cells` cells per side (0 = by zoom as before; a power of two 16..512; defaults 0, 0, 128, 128, 128: z12 44 m, z11 88 m, z10 176 m at 55 N); a tile a seed world's airport touches keeps the zoom's finer grid (the 1 cm fence rule). The grid is a function of zoom and profile, so neighbours still share their lattice. The build checks for cancellation every 16 rows of the patch and between TIN, sink and assembly (`tin::build_terrain_tile_until`, `worker::build_terrain_data_until`): a job cancelled by a reconfigure or a cover change stops instead of finishing a stale tile. The TIN half moved to `terrain/tin_build.rs` (`tin.rs` 903 -> 585 lines, the vendored Delatin). `perf_terrain_tin_build` (6 hill tiles per ring, thread CPU): T2 17.5 -> 5.0 ms (max 17.7 -> 5.2), T3 19.0 -> 5.4 ms (22.4 -> 6.3), T4 20.6 -> 5.8 ms (22.4 -> 6.3); T0 / T1 unchanged (1.5 / 4.9 ms). ### API: `WorldStreamer` (Node, registered by the GDExtension; entry symbol `gdext_rust_init`)

Methods (all `#[func]` in `rust/src/streamer.rs`). Per-frame call order: `update_camera`, `take_origin_shift`, `poll_ready`, `poll_fades`, `poll_unload`. Coordinates: Y-up, x = east, z = -north, meters, relative to the current floating origin.

| Method | Description |
|---|---|
| `configure(origin_lat: f64, origin_lon: f64, tile_url: String, cache_dir: String)` | Sets the origin and data source and (re)starts the workers. Empty `tile_url` = deterministic synthetic city. Re-calling it drops the old scheduler; everything already delivered is returned by the next `poll_unload`. |
| `update_camera(local_pos: Vector3, velocity: Vector3, alt_agl_m: f64)` | Every frame. Recomputes the quadtree cover (3D slant distance, look-ahead, hysteresis) and queues jobs. Triggers a floating-origin re-center when the camera is more than 5000 m from the origin. |
| `poll_ready(max: i32) -> Array<Dictionary>` | Finished tiles, at most `max` (the bridge asks for 2). Every requested tile is delivered, even when empty. Light re-deliveries (clustering above ~3000 m AGL) are limited to 1 per frame. |
| `poll_unload() -> PackedStringArray` | Tile keys (`z/x/y`) to remove. |
| `poll_fades() -> Dictionary` | Key (`z/x/y`) to `fade` (float 0..1) for every tile in a LOD transition. Incoming tiles go 0 to 1, outgoing 1 to 0, summing to 1. Driven by slant distance, force-completed after 3 s. Tiles not listed have fade 1. |
| `take_origin_shift() -> Vector3` | Non-zero once after a re-center; the host subtracts it from the camera and all tile roots in the same frame. |
| `debug_stats() -> Dictionary` | `queued`, `fetching`, `meshing`, `loaded` (each `PackedInt32Array` of length 4, indexed by ring), `cache_mb` (float), `origin_lat`, `origin_lon` (of the current local origin), `version` (String, e.g. `simplane_world 0.5.0 (build debug @...)`). |
| `debug_tiles() -> Array<Dictionary>` | One entry per tracked tile: `key`, `ring` (0..3), `state` (`queued`, `fetching`, `meshing`, `ready`, `failed`, `unloading`), `min`, `max` (`Vector2`, tile rect corners in local x/z meters). |
| `ground_height_at(local_x: f64, local_z: f64) -> f64` | Terrain height (m) under a local x/z point, through the current floating origin. Returns 0 (no DEM yet). |

Ready-tile dictionary (`poll_ready`): `key` (String `z/x/y`), `ring` (int 0..3, = 16 - z), `origin` (Vector3), `mesh` (Array in `Mesh.ARRAY_MAX` layout: VERTEX, NORMAL, COLOR, TEX_UV, INDEX; empty for R3 and empty tiles), `ground` (Array in `Mesh.ARRAY_MAX` layout: VERTEX, NORMAL, COLOR, INDEX; sent on every delivery, empty for R3 and tiles without ground), `lights` (PackedVector3Array relative to `origin`), `light_colors` (PackedColorArray; rgb = average colour, a = `clamp(sqrt(count) / 8, 0.125, 1)`). Lights are filled for R2 and R3 only.

Encodings:

- Building vertex COLOR: `r` = profile id / 8 (0 residential, 1 office, 2 retail, 3 industrial, 4 civic, 5 unknown), `g` = seed 0..1, `b` = floor height / 10 m, `a` = building height / 400 m. UV = meters (u along wall, v up).
- Ground COLOR: `r` = class / 16 (0 grass/park, 1 forest, 2 water, 3 residential, 4 commercial, 5 industrial, 6 other landuse, 8 road), `g` = lit road flag, `b` = road class / 8 (0 for areas), `a` = 1.

Guarantees: refining requests all 4 children as one sibling group; every requested tile is delivered; a parent is unloaded only after its 4 children were delivered and the swap fade finished; when coarsening, the parent is delivered again before its children are unloaded. Visibility rule (evaluated by the host): see `docs/contract.md` section 5 (until P2 it lived in `.claude/agents/godot-csharp-integrator.md`).

### Rings and data

- Quadtree cover: R0 z16 < 0.6 km, R1 z15 < 2.5 km, R2 z14 < 7 km, R3 z13 < 25 km. R0 full buildings and all roads, R1 boxes, R2 merged coarse blocks, R3 light points only.
- Sources: PMTiles v3 over HTTP range requests with a disk LRU cache (300 MB cap), or the synthetic city. Layers `buildings`, `landuse`, `roads` (see `data/README.md`).
- Environment variable `SIMPLANE_PROFILE=1` prints main-thread profiling lines (to be replaced by a `Diagnostics` setting in P1).
