# Test bench: diagnostics and performance measurement

Moved out of `low-poly-map/CLAUDE.md` on 2026-10-30. Paths are relative to `low-poly-map/`. To run a measurement, use the `/bench-measure` skill.

## Diagnostics (performance measurement; `scripts/Diagnostics/`, namespace `LowPolyMap.Diagnostics`)

The same approach as the SimPlane game's `Diagnostics/` (copied and adapted: `PerfMonitor`, `PerfStats`, `DurationHistogram`, `PerfMarker`, `JsonText`, the F4 overlay, `--benchmark` / `--soak`, per-machine baselines), so CPU, GPU, memory and draw calls are measured the same way in both projects. Host-only: the addon carries just a small allocation-free timing surface (`StreamerTimings`, `WorldView.Timings.cs`, wrapped around the facade calls).

- **Per frame** (`DiagnosticsNode`, process priority lowest of the scene, created by `BenchArgs`): `PerfMonitor.Frame()` takes the wall frame time (Stopwatch, not Godot's delta), `TimeProcess` / `TimePhysicsProcess`, draw calls, primitives, video and static memory, and the root viewport's measured render CPU / GPU time (`ViewportSetMeasureRenderTime`); it feeds the session stats (mean, p50 / p95 / p99, max, 1 % low, hitches, frames over 33.3 ms), a 1 s window and a 300-frame ring for the graph. **GPU time is 0 on Metal** (Godot 4.7.2 returns no viewport timestamps, same as the game's Forward+ finding): the result says `gpu_frames: 0`; with vsync off the frame time is the cost to compare.
- **Markers** (`PerfMarker`, 0.01 ms histograms and Godot custom monitors `SimWorld/<name>_ms`): `update_camera`, `poll_ready`, `fades`, `unload`, `origin_shift`, `debug_stats` are the main-thread time inside those library calls (the facade measures them for every caller; they are the calls only, not the host work around them), `upload_vector` / `upload_terrain` / `upload_landmarks` are the host upload time per layer (deltas of `WorldView`'s cumulative upload counters), `overlay` is the F1 refresh plus the F4 text and graph. Host work around the calls has its own markers: `unload_apply` (applying the `poll_unload` batch: cover removal, hide, retire), `fade_apply` (parsing and applying the `poll_fades` dictionary, material switches) and `release_drain` (the time-sliced clearing of retired node sets), all from `WorldView.LastUploads`. Nested scopes count twice (the F1 refresh contains its `debug_stats` read).
- **Once a second** (`SecondSampler`): `debug_stats()` `memory_mb` (total, data_tiles, height_tiles), `jobs_queued` / `jobs_running`, `data_tiles_loaded`, tiles loaded per layer and queued, host pool nodes; process memory (`ProcessMemory`: physical footprint through `proc_pid_rusage` on macOS, working set elsewhere, microseconds, no child process), `OS.GetStaticMemoryUsage`, `GC.GetTotalMemory(false)` and the managed allocation rate (`GC.GetTotalAllocatedBytes` delta). Each is a `Series` (min / max / last / mean / least-squares slope per minute).
- **Frame split** (`frame_split` in the result, `frame_ms` / `process_wall_ms` / `render_cpu_ms` / `other_wait_ms` per second): script work = wall time from the first to the last `_Process` of the frame (`DiagnosticsNode` opens the timer, `ProcessTail` closes it), physics and render CPU from Godot's monitors, GPU where the driver reports it, and `other_wait` = what is left (presentation, GPU wait, idle; never below 0). Together with the CPU use below it says CPU-bound or waiting: the result's `verdict` compares the main thread's CPU % with 90.
- **CPU use** (`CpuTimes`, per second, 100 = one core): `cpu_process_pct` (all threads, .NET `TotalProcessorTime`), `cpu_main_thread_pct` (`ThreadClock`: `clock_gettime(CLOCK_THREAD_CPUTIME_ID)`, macOS and Linux), `cpu_other_threads_pct` = process minus main thread = the Rust workers plus Godot's render / audio / GC threads. `debug_stats` does not expose the library's worker CPU, so the two cannot be separated further (the library's own `SIMPLANE_PROFILE=1` log has per-job CPU).
- **Visibility churn** (counters in `TileCover`, per layer, `visibility_churn` and `*_per_s` series): tiles shown / hidden, **quick toggles** (the same tile changed shown/hidden twice within 1 s: the flicker candidates), fades (sibling swaps) started / ended / active, re-deliveries (a key delivered again less than 10 s after it was removed). Landmark tiles have their own cover and are not counted.
- **Uploads** (`uploads`, `upload_*` markers): tiles per layer, frames that uploaded, frames over the upload budget (`WorldRenderSettings.UploadBudgetUs`), tiles per uploading frame, the worst frame's ms. `burst_frames` = frames that ran with the burst budget (a deep backlog and a camera below 60 m/s: `UploadBudget`, `WorldRenderSettings.UploadBudgetBurstUs` 4 ms / 4 tiles; steady flight keeps 2 ms / 2 tiles); `sprite_fill_r<N>_*` = host time to pack and upload the sprites of a tile per ring; `config.fill_s` / `fill_tiles` = the cold fill: seconds into the settle phase of the last tile upload and the tiles uploaded by then.
- **Stalls** (`stalls` in the result, `StallLog`): the GC pause total and the frames with a pause of 1 ms or more; the three longest frames with their GC pause (`GC.GetTotalPauseDuration` delta), the wall AND thread CPU time of every library call (`StreamerTimings.MeasureThreadCpu`; wall far above CPU = descheduled or suspended inside the call, wall equal to CPU = the call worked or a GC ran on that thread) and the `PerfMarker` categories of that frame.
- **Managed allocation by site** (`gc.main_thread` in the result, `AllocProbe` in the addon, `AllocReport`): the main thread's `GC.GetAllocatedBytesForCurrentThread` booked to the sites of the frame loop, exclusive of nested sites (`update_camera`, `ground_height`, `poll_ready` call / `ready_parse` / `ready_lights`, `upload_*`, `set_sprites`, `poll_fades` / `fade_read`, `poll_unload`, `lod_read`, `shader_globals`, `view_frame` = what `WorldView._Process` itself allocates, the host's `host_ui` / `host_bench` / `host_sampler`, ...), with bytes, calls, bytes per call and KB/s per site, the thread total, `unattributed_per_frame` (what no site claims; 25 B per frame now) and `other_threads_bytes`. A scope is a static read and a branch when the probe is off; the diagnostics node turns it on. This is how the garbage was ranked; add a site where a new per-frame path appears and look at the top of the list after any change that touches the frame loop.
- **Collections** (`gc.events` in the result, `GcEvents`): one entry per collection of the measured part with generation, pause, survivors (`promoted_kb`), `finalization_pending`, LOH size, gen0 size (the 8 MB budget) and whether it was concurrent; `gc.server_gc` / `latency_mode` / `pacer_*`. What the pause is made of (measured with `--gc-trace`): the .NET collector marks every handle in the process, and a Godot world has tens of thousands (one wrapper per node / mesh / material in the pools, a `WeakReference` per live `Godot.Collections` wrapper in Godot's `DisposablesTracker`, a finalizable `Variant.Disposer` per Variant that holds an Array / Dictionary / String / Packed array); a gen0 collection takes 5 to 10 ms for that alone (about 3 ms between the dependent-handle and finalization-queue marks), whatever the garbage is. So cutting collections matters more than cutting bytes, and every wrapper the frame loop creates and does not `Dispose()` makes the next one longer. A gen2 (10 to 30 ms) comes from the large-object heap budget (about 3 MB): the per-tile light arrays above 85 KB.
- **Reading the library without garbage:** every `Variant` and `Godot.Collections` wrapper taken from a call or a dictionary is disposed at once (`using var v = _node.Call(...)`, `Dispose()` on the values read), argument arrays are reused, `StringName`s are static (`ShaderGlobals.HourName` ..., a `const string` converted to a StringName per call allocated a finalizable object per call), `PollFades` returns null for an empty dictionary, `poll_ready` is read into a reused list (`WorldStreamerFacade.PollReady(max, List<ReadyTile>)`; the caller releases the mesh handles of a tile with `ReadyTile.ReleaseHandles()` after the upload, which also frees the delivered vertex bytes at once instead of at the next collection), the one-element Array for engine surfaces is reused (`MeshSurfaces` is an instance per pool), the `debug_stats` key names of the latency table / `memory_mb` / extra counters are collected once per dictionary size and the values looked up by StringName, `StreamerStats.Latency` stage objects are reused. A wrapper per `poll_ready` / `poll_fades` / `poll_unload` call remains (208 + 208 + 122 B per frame, 540 B and three finalizable objects: the library returns an Array, a Dictionary and a PackedStringArray every call, empty or not; fixing that needs a scalar from the library, see the report of the round).
- **GC pacing** (`GcPacer`, `WorldRenderSettings.GcQuietBudgetMb`, `--gc-quiet`): the runtime's gen0 budget (8 MB with concurrent GC) cannot be raised from a runtimeconfig (`System.GC.Gen0Size` / `Gen0MaxBudget` / `Concurrent=false` were tried: only the environment variable `DOTNET_GCgen0size` changes it, and the project's `runtimeconfig` is not even read by the editor binary the bench runs in), so the view asks for a no-GC region at run time: `GC.TryStartNoGCRegion(budget)` takes 0.4 ms, commits memory only as it is allocated and ends the pauses for as long as the budget lasts; at 85 % the pacer ends the region and starts the next; the start itself runs one full blocking collection (CoreCLR's `StartNoGCRegion` collects `max_generation` to make the budget free), so the pacer no longer adds a `Collect(0)` of its own. One pacer per process (`GcPacer.Acquire` / `Release`, `Tick` once per process frame whichever view calls first); a refused start backs off 10 s (a refused start may have run a full collection: retrying every frame under memory pressure would collect every frame), an OS memory warning ends the region, collects and holds the pacer 60 s, `RotateNow()` rotates at a quiet moment the game knows (menu, pause, loading), the last view's `_ExitTree` ends the region with a full collection and `WaitForPendingFinalizers` (measured: ending it without one aborted the quit, `mutex lock failed`, the finalizer thread reaching the engine during its teardown; leaving it open was safe only because Godot's own shutdown collection ended it). Trade-offs: the working set grows by up to the budget (RSS 36 to 139 MB in a 100 MB test); finalizable garbage and the native memory of any un-disposed wrapper wait for the rotation; a rotation costs 14 to 17 ms because the collection that was put off has more finalizable objects to walk; an allocation burst above the budget ends the region early (an ordinary collection, then the pacer restarts it, `pacer_early_exits`); other code calling `GC.Collect` ends it too. Measured and not kept: `GCSettings.LatencyMode = SustainedLowLatency` (2 runs against 2 without, same code, `--gc-quiet=0`: the same three gen0 collections of 6.6 to 9.2 ms; no gen2 fell into those four runs, so its effect on a gen2 is unmeasured), `gcConcurrent=0` through the environment (Batch mode: gen0 pauses 6.5 to 8.5 ms, unchanged); `LowLatency` (no gen2 at all) was not tried, it is not safe for a long session. **Measured on 2026-10-29 (600 s `low-250` soak, release library, fullscreen, same path, `bench_results/soak-gcq0.json` / `soak-gcq64.json`; the machine was not idle, load 4 to 5, so the absolute numbers are noisy but the two runs share it):** off: 30 collections (every 17 to 24 s), pauses 7.5 to 27.7 ms, 383 ms of pause in all, frame p50 3.5 ms / p99 7.75 ms, last minute 314 fps, managed heap flat (28 to 52 MB), process memory +13 MB/min. 64 MB: 5 rotations (every 108 to 155 s, `pacer_early_exits` 0, `pacer_refused` 0), the one rotation the event poll caught was a gen2 of **184 ms** with 283 k objects pending finalization and 49 MB promoted (`pacer_rotation_ms_max` 184; the others stayed under 33 ms); the managed heap grew from 38 to 226 MB and never came back (the finalizable wrappers of a whole region survive their rotation to be finalized and are freed only at the next one), process memory +40 MB/min, and the frame time doubled over the run: last minute p50 7 ms, 145 fps (first minute 3.25 ms / 310 fps). 16 MB (`soak-gcq16-trace.json`, `--gc-trace`): 23 rotations and 4 early exits, worst rotation **224 ms** (a 226 ms frame followed by a 79 ms one at 546 s), heap 39 to 261 MB (+15 MB/min), last minute again 145 fps / p50 7 ms: the budget changes the cadence, not the outcome. So at either budget the pacer is a net loss on this workload: fewer pauses, one of them 7 times longer, plus a growing heap and a slower steady state. The root cause is the finalizable-object rate (about 2200 per second at 310 fps: the three poll wrappers per frame and the per-tile light arrays), which no budget removes; cutting it (the pending-counts call, api 1.12 candidate) comes before any pacing. `GetGCMemoryInfo` returns empty or stale records inside a no-GC region (`gc.events` had zeros for 3 rotations and a duplicate), so `--gc-trace` is the way to read rotation pauses. An exported game would get the same effect from `GcQuietBudgetMb` on its `WorldRenderSettings` or from `DOTNET_GCgen0size` in its launcher; after the soak the recommendation is to leave it at 0.
- **Per layer draw proxy**: shown tiles inside the camera frustum and their triangles per layer (`vector_tiles_in_frustum` ..., one mesh instance per tile; sampled once a second, it costs about 1 ms of the 1 Hz part).
- **Noise** (`noise` in the result): load averages and the other busy processes before and after the run (`sysctl vm.loadavg`, `ps`). **Numbers from a loaded machine are noisy and must not become baselines**: `--update-baseline` only on an idle machine (check `noise.before`).
- **Cost of measuring** is in every result (`diagnostics_overhead`: the per-frame part, the 1 Hz part, and `frame_allocated_bytes`, which must be 0).
- **Result** (`BenchmarkReport`, one JSON file): config (path, hour, view, edges, tau, terrain), end state (the same numbers on two runs mean the same path), build (commit and dirty flag, Godot, library version / api / flavour), machine, `perf`, `markers`, `gc`, `diagnostics_overhead`, `series`, for a soak `soak.first_minute` / `last_minute` / `after_first_minute` / `memory_slope_mb_per_min`, and `baseline`.
- **Baselines**: none is committed yet: write them with `--update-baseline` only when the machine is idle (`noise.before.load_avg` below the core count, no browser / build running; the 5 benchmarks take about 8 minutes). `bench_results/baselines/<machine>.json` (machine = `OS.GetModelName()`, here `Mac14-9`) is committed once recorded, one entry per `<benchmark>@<release|debug>` (a debug library is several times slower, so flavours never compare), with `@gcq<MB>` appended when the run had the collector pacer on (`--gc-quiet`), so a paced run never compares with or overwrites an unpaced entry; the rest of `bench_results/` is ignored by the VCS (`.gdignore` keeps Godot out of it). A frame p95 more than 10 % above the entry sets `"regression": true` and warns. Write the entry with `--update-baseline`. Which library runs: the editor binary has the `debug` feature, so `simplane_world.gdextension` loads `macos.debug`; for release numbers run `cargo build --release`, point `macos.debug` at the release dylib for the run and restore it afterwards. The result says `library_flavour` from the library's build marker.
- Measuring run: `$G --path . -- --benchmark=low-250 --seconds=60 --quit --tile-url=http://127.0.0.1:8787/vilnius-v2.pmtiles --cache-dir=user://cache_bench` (a fresh checkout needs `$G --headless --path . --import` once; the first cache fill happens in the settle phase). Soak: `--benchmark=low-250 --soak=600`.
- Benchmarks (`BenchmarkDef.All`; paths in `Diagnostics/FlightPaths.cs`): `low-250`, `climb`, `zoom`, `night-low`, `reconfigure` fly the real Vilnius archive; `seed-low` flies the same racetrack over the generated Vilnius of the two-cities seed world (`BenchmarkDef.World`; no tile server, no `--tile-url` / `--cache-dir`), so seed work (generator 4) has a host cost number: `$G --path . -- --benchmark=seed-low --seconds=60 --quit --out=seed-low.json`. Its baseline key is `seed-low@<flavour>`; record it with `/bench-measure seed-low baseline` on an idle machine. Details of the arguments: `keys-and-args.md`.
- Limits: the GPU time above; numbers from a machine that runs other work (a second Godot, a build) are noisy; `TimeProcess` reads higher than the frame time (as in the game) and is reported as Godot gives it.
