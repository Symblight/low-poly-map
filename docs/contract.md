# WorldStreamer contract

api_version: 1.7

This is the only full statement of the contract between the SimWorld library (the Rust `WorldStreamer` GDExtension node, crates `simworld-core` + `simworld-godot`) and any host that displays it (today the C# test bench in `low-poly-map/`, later the SimPlane game). Everything a host may rely on is here; everything else is an implementation detail.

The line `api_version: <major>.<minor>` above is checked by `cargo test` against `simworld_core::API_MAJOR` / `API_MINOR`, and every `#[func]` and `#[signal]` of `WorldStreamer` must appear in this file. Each section and table row carries the `api_version` that introduced it (**[0.5]**, …).

## 1. Versioning and change rules [0.5]

- `api_version` is the contract version `major.minor`. It is independent of the crate version (`debug_stats()["version"]`) and of the crate patch level.
- **Minor bump = additive only:** a new method, signal, dictionary key or optional argument. Existing methods, keys, encodings and guarantees keep their meaning. A host written for `0.x` works on any later `0.y` with the same major.
- **Major bump = breaking:** a removed or renamed method/key, a changed type, encoding or guarantee. A host must refuse to drive a library with a different major.
- **Host check:** read `api_version()` once after creating the node (or `debug_stats()["api_major"/"api_minor"]`). A library without either predates `api_version` (crate 0.5.0-spike); hosts then fall back to probing method names. A lower minor than the host expects means the features introduced after it are missing; the host should say which ones.
- **Changing the contract:** any change updates this file, `API_MAJOR`/`API_MINOR` in `rust/simworld-core/src/lib.rs` and `CHANGELOG.md` in the same commit. New items get the new version tag. The agent files (`.claude/agents/*.md`) only point here.

## 2. Coordinates and units [0.5]

- **Local frame = Godot axes:** Y-up, **x = east, y = up, z = −north** (−Z faces north). Meters. Angles in degrees, WGS84 lat/lon.
- Rust keeps all world math in f64 (fixed ENU frame at the configured origin). Everything handed to the host is f32/f64 **relative to the current floating origin**.
- **Floating origin:** when the camera's horizontal local distance `hypot(x, z)` from the origin exceeds **5000 m**, `update_camera` (or `update_camera_geodetic`) moves the origin onto the camera (translation only, never rotation; the shift's `y` is always 0). The shift is reported once by `take_origin_shift()`; the host subtracts it from the camera and every tile root in the same frame. **[0.7]** The same shift is also emitted as signal `origin_shifted(shift)` during that call (section 3.4), for any other node in local space. All positions handed out after the call that re-centered (`poll_ready` origins, `debug_tiles` rects, `ground_height_at` / `local_to_geodetic` input, `geodetic_to_local` output) are in the post-shift frame.
- **Heights [0.7]:** local `y` = meters above mean sea level. Local space is flat (no Earth curvature): the terrain is at `y = ground_height_at(x, z)`, building bases stand on it. **[1.4]** The terrain is 0 everywhere unless the host requested the layer `terrain` (section 3.1) and the profile enables it (`terrain.enabled`, section 3.2); then it is a seeded procedural height function (no data). **[1.5]** The same host then also receives the terrain mesh (layer `terrain`, section 9a); the drawn TIN differs from `ground_height_at` by at most the band's `max_error_m × detail_scale` (vertical), which the drape lift of the vector world covers (section 9). **[1.7]** The TIN is sunk under the height function (section 9a "Sink"): at its lattice samples it lies on or under `ground_height_at` and at most twice the error under it. **[1.7]** In a seed world (section 3.1 `seed_world`) the height function also carries the world's data rules, in this order: the field, then the **water rule** (the sea is flat at `terrain.sea_level_m`, each lake flat at its level = the lowest field height on its outline, 1 cm; land within `seed.water.blend_m` of the sea or a lake slopes down to it; rivers are not part of the rule), then the **runway strips** (each open runway level: along its centreline linear between the heights at its two landing thresholds, slope at most `seed.airport.max_slope`, constant across its strip; runways whose strips overlap or come within 1 m of each other (crossing or close parallel runways, approximate runways centred on the same reference point) form a group that shares the profile of its longest runway (ties: the first designator), measured along that runway's axis, so the function never steps on a runway; the rest of the airport fence at the height of the nearest strip point; outside the fence blended into the surroundings over `seed.airport.shoulder_m`). `ground_height_at`, building bases, the ground drape, lights, the cover boxes and the terrain mesh all use it, so a runway is level and the sea is flat in every output.
- `debug_stats()["origin_lat"/"origin_lon"]` is the WGS84 position of the *current* origin (it moves with re-centering).
- **Tile keys** are Strings `"z/x/y"` (slippy-map / XYZ scheme, y down from the north, Web Mercator). Zooms 13..16 only. `ring = 16 − z` (R0 = z16 … R3 = z13).
- **[1.5] Layers:** the keys above are the vector layer (`layer` = `"world"`). Terrain tiles (`layer` = `"terrain"`, section 9a) have keys `"t/z/x/y"` (the `t/` prefix is the layer; the two layers never share a key), zooms `terrain.far_zoom..terrain.near_zoom` (default 10..14) and `ring` = index in `terrain.bands` = `near_zoom − z` (T0 = z14 … T4 = z10 by default). They reach only a host that requested the layer `terrain` with a profile that enables it (section 3.1); any other host never sees a `"t/…"` key in `poll_ready`, `poll_fades`, `poll_unload` or `debug_tiles`. A host keeps one tile map per layer and evaluates the visibility rule (section 5) per layer.
- Mesh positions, light positions and ground positions are relative to the tile's `origin` (tile center, y = 0).
- **Triangle winding:** clockwise seen from the front (Godot's front face), for buildings, ground and **[1.5]** terrain (surface clockwise seen from above, skirts seen from outside).

## 3. Methods [0.5]

Class `WorldStreamer` extends `Node`, registered by the GDExtension (entry symbol `gdext_rust_init`). It is not a tool class (runs in-game only). Create it with `ClassDB.Instantiate("WorldStreamer")` and call it through `GodotObject.Call(...)`, from the **main thread only**. Every method is non-blocking; `update_camera` and `poll_*` target < 0.5 ms. Before `configure` / `configure_world` (and **[0.7]** after `shutdown()`) every method is a harmless no-op returning an empty value (`Vector3.ZERO`, empty Array/Dictionary/PackedArray, 0; `api_version` works always; `world_profile` returns the defaults or the last profile; `status()` returns its idle shape, section 3.5). Errors never panic across FFI: they are logged (`godot_warn!` / `godot_error!`, rate-limited) and retried with backoff.

**Per-frame call order [0.5]:** `update_camera` (**[0.7]** or `update_camera_geodetic`) → `take_origin_shift` → `poll_ready` → `poll_fades` → `poll_unload`. Re-centering and fade progress happen inside `update_camera`. A fade started by a `poll_ready` delivery is already in the same frame's `poll_fades`; a fade that completes is reported by `poll_fades` and its outgoing tiles are in the same frame's `poll_unload`.

### 3.1 `configure_world` options and result [0.6]

`options` keys (unknown keys are logged as a warning and ignored, so a host written for a later minor can pass newer keys):

| Key | Type | Required | Meaning |
|---|---|---|---|
| `origin_lat`, `origin_lon` | float (int accepted) | yes | World origin, WGS84 degrees: latitude within ±85.0511 (Web Mercator), longitude within ±180 |
| `tile_url` | String | no (default `""`) | As in `configure`: `http(s)://` `.pmtiles` URL, empty = synthetic city. Any other scheme is an error. |
| `cache_dir` | String | no (default `""`) | As in `configure` |
| `profile_path` | String | no | World profile JSON file (`res://`, `user://` or an OS path; read through Godot's file system). Partial files are fine. Omitted = the defaults. |
| `profile_overrides` | Dictionary | no | Partial world profile merged onto the file (or the defaults): same keys and nesting as the JSON, objects merge deeply, arrays and scalars replace. | `diagnostics` | Dictionary | no | `profile` (bool: log a phase breakdown for main-thread calls slower than 1 ms), `warnings_per_second` (int 1..1000, default 5). Omitted keys keep their current values (initially the host defaults, e.g. `SIMPLANE_PROFILE=1`). |
| `layers` | Array of String (or PackedStringArray) | no (default `["world"]`) | **[1.4]** The layers the host draws. Known: `world` (the vector world; always on) and `terrain`. The terrain is active only when `layers` contains `"terrain"` **and** the profile has `terrain.enabled = true`; a profile that enables it without the layer stays flat and logs one warning per configure: `terrain.enabled ignored: host did not request layer "terrain"`. An unknown name is an error (`layers: unknown layer "x" (known: world, terrain)`), nothing changes. A host passes `"terrain"` only once it can draw the terrain (or accepts a vector world standing on undrawn relief). **[1.5]** With the terrain active the host also receives the terrain layer (`"t/…"` keys, section 9a): passing `"terrain"` means "I draw terrain tiles". |
| `seed_world` | String | no (default none) | **[1.7]** Path of a world seed manifest `world.json` (`docs/spec-world-seed.md` section 4; `res://`, `user://` or an OS path, read through Godot's file system; the paths inside it are relative to its folder unless they carry a scheme). With it every vector tile is generated from the seed files (section 3.6) and the terrain carries the water and runway rules (section 2). Requires: `tile_url` empty, `layers` containing `"terrain"`, the profile's `terrain.enabled` = true and `terrain.flat_radius_m` = `terrain.flat_blend_m` = 0 (the default profile has 1500 / 2000: pass both as 0 in `profile_overrides`). Errors (nothing changes): ``seed_world: tile_url must be empty (a seed world generates every tile), got `<url>` ``, `seed_world: needs the terrain layer: pass layers ["world", "terrain"]`, `seed_world: needs terrain.enabled = true in the world profile`, `seed_world: terrain.flat_radius_m = 1500 must be 0 (...)` (same for `flat_blend_m`), `seed_world <path>: cannot read the manifest: <reason>`, and the file errors of the spec's section 4.6, each naming the file, the key path and the value, e.g. `seed_world <path>: <dir>/cities/kaunas.json: radius_km: 45.0 is above the maximum 30` (several joined by `; `). Loading takes a few hundred ms (the water index); a later `configure_world` with unchanged files and unchanged profile `seed` / `terrain` keys reuses the loaded world (no reload). Without the option (or empty) the world is unchanged byte for byte. |
| `terrain_center` | Array of 2 numbers `[lat, lon]` (or PackedFloat64Array, `Vector2` = (lat, lon)) | no (default = `origin_lat`, `origin_lon`) | **[1.6]** Centre of the terrain's flat zone (profile `terrain.flat_radius_m` / `flat_blend_m`). Without it the flat zone is centred on the configure origin, so a host that reconfigures with a new origin (a teleport, the bench's F3 apply) moves the flat zone and with it the relief near the camera; passing the same centre every time keeps the heights where they were. Latitude within ±85.0511, longitude within ±180, else an error (`terrain_center = (lat, lon) is out of range ...`), nothing changes. Ignored when the terrain is not active. |

|---|---|---|
| `ok` | bool | The configuration was applied |
| `error` | String | Why not (empty when `ok`). Profile errors name the key, the value and the allowed range, e.g. ``profile: bands.hysteresis = 3 is out of range [1.01, 2]`` or ``profile_overrides: unknown key `bands.r0_edge` ``. |
| `api_version` | Vector2i | Same as `api_version()` |
| `attributions` | PackedStringArray | Attribution strings the host must show while map data is visible: `["© OpenStreetMap contributors"]` for a `tile_url` source, empty for the synthetic city, **[1.7]** a seed world's strings (see `attributions()`). On failure, those of the configuration still running. |

On success it behaves like `configure` (teleport): the old workers and cover are dropped, every tile delivered before is returned by the next `poll_unload`, the disk cache is kept. On failure nothing changes (the previous configuration keeps running, nothing is unloaded).

**Cache folder lock [0.7]:** when `tile_url` and `cache_dir` are both non-empty (**[1.7]** or, for a seed world, when `cache_dir` is non-empty and a city file has a `real.url`, so a later real source never fails on the lock; a seed world without URL sources takes no lock and needs no `cache_dir`), `configure_world` (and so `configure`) creates `cache_dir` if missing and takes an exclusive lock on `cache_dir/.simworld.lock` **synchronously**, before anything changes and before any asynchronous archive or cache open. If another node or process holds it, the result is `ok: false`, `error: "cache_dir in use: <cache_dir>"`, and nothing changes. Section 11a has the full lifecycle rules.

**Tileset contract check [0.6]:** the archive is opened asynchronously (a warm cache works offline, so `configure_world` never waits for the network). When it opens, its header zoom range must cover 13..16 and its metadata `vector_layers` must contain `buildings`, `landuse` and `roads`. On a mismatch an error naming the problem is logged once (`godot_error!`) and every fetch from that archive fails (logged, rate-limited, retried with backoff); `configure_world` itself has already returned `ok`. The synthetic city and **[1.7]** a seed world are exempt.

### 3.2 World profile [0.6]

Every tuning value of the world is data: band edges, hysteresis and look-ahead; building and ground Douglas-Peucker tolerances and minimum areas; per-band minimum building height (profile_version 2); fetch and mesh concurrency, re-delivery pacing and retry backoff; light carpet altitudes and cell size; the fade safety cap; the re-center distance; cache cap and HTTP timeouts; light profiles (building kinds → profile, sprite colors, landuse fallback; **[1.0]** window widths and hourly lit shares, the landmark floodlight, overrides by OSM id, dark state tags, the slender-tower heuristic, the minimum window wall height); road classes (highway values), widths and link rule; area groups (landuse kinds → class and stacking level) and the per-band lift step.

- **Files:** `addons/simworld/profiles/default.json` lists every key with its default (= the compiled-in defaults, the values in sections 2, 5, 8, 9 and 10; pinned by `cargo test`). `addons/simworld/profiles/world-profile.schema.json` (JSON Schema 2020-12) documents every key with units and allowed range. The core checks values itself (`simworld-cli validate-profile <file>` runs that check); the schema is for editors and humans.
- **Partial profiles:** every key is optional; omitted keys keep their defaults. Objects merge deeply (`profile_path` file first, then `profile_overrides`), arrays and scalars replace. `ground.areas` is a map with free group names (a new name adds a group).
- **`profile_version`** (int, today **6** **[1.7]**; 5 since 1.4): a file (or overrides) with the library's version or older is strict, an unknown key is an error (a typo). A newer version loads: unknown keys are logged as warnings and ignored, known keys apply. The resolved profile (`world_profile()`) always carries the library's version.
  - Version history: **1** (api 0.6) the initial key set. **2** adds `buildings.r0.min_height_m`, `buildings.r1.min_height_m`, `buildings.r2.min_height_m` (default 0) and changes the default of `fades.cap_s` from 3.0 to 0.75. **3** adds `lights.min_ring` (0..3, default 2 = R2/R3 only, section 8; **[1.0]** the default is 1 = R1..R3 within version 4, see below). **4** **[1.0]** adds the light profiles `lights.profiles.landmark` and `lights.profiles.dark`, `lights.profiles.{residential,office,retail,civic}.windows` (`width_m`, `lit_share`), `lights.profiles.landmark.floodlight` (`strength`, `fade_height_m`), `buildings.overrides`, `buildings.dark_states`, `buildings.slender_tower` (`ratio`, `max_area_m2`) and `buildings.min_window_wall_m`, changes the default of `lights.min_ring` from 2 to 1 (R1 carries light sprites that the host cross-fades with the window average, W4), and moves kinds out of `civic` and `industrial` (light profiles, below). **[1.1]** Also within version 4 (still unreleased): `lights.street` (`min_ring` 0..4, `color`, `alt_color`, `alt_share` 0..1, `spacing_m`, `height_m`, `untagged_max_class` 0..6; street lamps, section 8). **[1.2]** Also within version 4: `lights.beacons` (`min_ring` 0..4, `min_height_m`, `level_spacing_m`, `corner_min_size_m`, `color`, `alt_color`, `alt_share`; beacons, section 8). **[1.3]** Also within version 4: `ground.r3` (same keys as `ground.r0..r2`; the R3 ground, section 9). **5** **[1.4]** adds the section `terrain`; **6** **[1.7]** the section `seed` and, also within version 6 (still unreleased), `fades.max_active` (0..256, default 4: most LOD swaps fading at once, section 6). A version 1, 2 or 3 file still loads strictly; the keys it lacks keep their defaults (a file that lists the old `civic` or `industrial` kinds now collides with `landmark` / `dark` and is rejected: drop the moved kinds). Profile keys are additive and versioned by `profile_version` alone: adding them does not change `api_version` (still 0.7).
- **Minimum building height [profile 2]:** `buildings.rN.min_height_m` (N = 0..2, 0..500 m, default 0 = keep all) drops a building from band N's **building mesh** when its resolved roof height is below the value. Resolved roof height = the same value the mesher extrudes to and encodes in COLOR `a` (section 7): tagged `height`, else `levels` × floor height, else the kind/landuse fallback, measured from the ground (a raised part's `min_height` is included, i.e. it is the top of the roof, not the part's own thickness), capped at 400 m. It is applied per feature before clipping, exactly like `min_area_m2` (a multipolygon building is one feature; every building part feature is judged on its own height). Mesh only: lights (single and clustered, R2/R3), ground, roads and landuse, the tile's box height used by the cover and every other output are independent of it. There is no R3 key: R3 has no building mesh. With the defaults the output is bit-for-bit unchanged (golden hashes).
- **Light profiles and resolution [1.0, profile 4]:** seven named profiles `residential` (id 0), `office` (1), `retail` (2), `industrial` (3), `civic` (4), `landmark` (6), `dark` (7); id 5 stays reserved. Each has `color` (sprite rgb; unused for `dark`) and `kinds`, one table holding OSM `building`, `historic` and `man_made` values; `windows` (`width_m` = window column width in meters, read by the mesher; `lit_share` = 24 hourly lit shares 0..1, read by the host shader) exists on residential, office, retail and civic only (no `windows` key = no windows); `floodlight` (`strength`, `fade_height_m`, host shader) on `landmark` only and required there. Defaults: landmark = castle, fort, tower, bell_tower, church, cathedral, chapel, mosque, synagogue, temple, monastery, shrine, gatehouse, city_gate, lighthouse, monument, memorial; dark = ruins, roof, carport, garage, garages, shed, barn, bunker, silo, storage_tank, slurry_tank, digester, chimney, water_tower, container, greenhouse, ship, service, transformer_tower, bridge (the religious kinds left `civic`, garage/garages/shed/barn/service/transformer_tower/greenhouse/storage_tank left `industrial`). A building's profile is the first match of: (1) `buildings.overrides` by OSM id (`"w123456": "landmark"`; `n`/`w`/`r` + digits); (2) a state tag listed in `buildings.dark_states` (default `historic=ruins`, `ruins`, `disused`, `abandoned`; entries `key` or `key=value` over the tile attributes `historic`, `man_made`, `ruins`, `disused`, `abandoned`) → `dark`; (3) the kind table for `kind`, and when `kind` is in no profile, for `historic`, then `man_made`; (4) for such generic kinds only, with a **tagged** `height` or `levels` and a footprint the tile encoder did not clip: `height ≥ slender_tower.ratio · √area` and `area < slender_tower.max_area_m2` (default 3.0, 150 m²) → `landmark`; (5) the landuse fallback. Then the `windows` tile attribute: `no` keeps the profile without windows; `yes` on a profile without `windows` switches the building to its landuse fallback profile if that one has windows, else to `residential` (if it has), so COLOR `r` and the light color are that profile's. Wall parts lower than `buildings.min_window_wall_m` (default 2 m) never get windows, and neither does any R2 wall (section 7).
- **Validation:** out-of-range values, wrong types, `r0_edge_m < r1_edge_m < r2_edge_m < r3_edge_m` violations, `cluster_off_agl_m > cluster_on_agl_m`, `retry_max_s < retry_base_s`, a building kind in two light profiles, a landuse kind in two area groups or a highway value in two road classes are errors. **[1.0, profile 4]** Also errors: a `lit_share` without exactly 24 values (or a value outside 0..1), `windows` on industrial / landmark / dark, `floodlight` on any profile but landmark or a landmark without it, an override id not matching `^[nwr][0-9]+$` or naming an unknown profile, a `dark_states` entry that is not `key` / `key=value` over the five state attributes (the flags take no value but `yes`). A `lit_share` that rises anywhere from 18 h to 3 h (wrapping at midnight) is a logged warning, not an error.
- **Not in the profile (structural, part of the tileset contract):** 4 bands over zooms 13..16 (`ring = 16 − z`), the layer names, the COLOR encodings (section 7, 9), the fade quantum, the light intensity formula (section 8).
- **Terrain [1.4, profile 5]:** section `terrain` (all keys in `default.json`, ranges in the schema): `enabled` (false), `seed`, `amplitude_m`, `feature_size_m`, `octaves`, `ridge_share`, `valley_share`, `plateau_share`, `sea_level_m`, `flat_radius_m`, `flat_blend_m` (flat zone around the configure origin, blended smoothly; re-centering does not move it), `exaggeration`, `height_offset_m`, `water_snap_m`, `drape_step_m`, `detail_scale_max`, and for the terrain-mesh layer (**[1.5]** used since 1.5, section 9a; validated since 1.4) `skirt_m`, `shading` (`flat` / `smooth`), `horizon_cull`, `horizon_margin_m`, `max_fetch`, `max_mesh` (`max_fetch` limits the dispatch only: terrain tiles have no fetch stage, so the layer is bounded by `max_mesh` jobs per ring), `near_zoom`, `far_zoom` and `bands[]` (`edge_m`, `max_error_m`, `max_edge_m`, `max_triangles`; one per zoom from `near_zoom` down to `far_zoom`). Errors: `near_zoom < far_zoom`, a `bands` length other than `near_zoom − far_zoom + 1`, non-increasing `edge_m`, `max_edge_m` between 0 and 500. A version 1–4 file loads strictly with the section at its defaults (terrain off). Takes effect only with the host layer `terrain` (section 3.1).
- **World seed [1.7, profile 6]:** section `seed` (all keys in `default.json`, ranges in the schema): `aeroway_class` (7, or 6 for a host without the class 7 branch, section 9), `water` (`blend_m` 400, `raster_n` 64), `airport` (`shoulder_m`, `strip_end_m`, `strip_half_m` / `taxi_offset_m` / `taxiway_width_m` / `runway_width_m` per airport type `large` / `medium` / `small`, `fence_margin_m`, `default_length_m`, `max_slope` 0.01, `lights` with `height_m`, `edge_spacing_m`, `approach_length_m`, `approach_spacing_m`, `approach_min_runway_m`, `taxiway_spacing_m`, `intensity` and five rgb colours), `countryside` (`forest_share`, `water_forest_share`, `water_distance_m`, `meadow_share`, `noise_cells`, `tint_levels`, `edge_warp`). Used only by a world configured with `seed_world`; a version 1–5 file loads strictly with the section at its defaults.
- A profile change never serves stale geometry: only raw tile bytes are cached (section 10).

### 3.3 Geodetic camera input [0.7]

For a flight model (e.g. JSBSim) that knows the aircraft geodetically. `update_camera_geodetic(lat, lon, alt_msl_m, vel_ned)`:

- (a) `lat`, `lon`: **WGS84 geodetic** degrees (\|lat\| ≤ 90, \|lon\| ≤ 180).
- (b) `alt_msl_m`: altitude **above mean sea level** (m). The library has no geoid model: a host whose flight model reports height above the WGS84 ellipsoid (JSBSim's geodetic altitude) must convert it to MSL itself (an ellipsoid-height variant is an open decision in `docs/spec-library-packaging.md`).
- (c) Height above ground = `alt_msl_m − ground_height_at` at that point (with the terrain off it is 0, so AGL = MSL; **[1.4]** with the terrain active, the procedural height); negative AGL counts as 0, as in `update_camera`.
- (d) `vel_ned`: m/s as `Vector3(north, east, down)`, mapped to local axes as **x = E, y = −D, z = −N** (vertical speed feeds the look-ahead as in `update_camera`).
- The position is converted through the current floating origin (as `geodetic_to_local`), then the call is identical to `update_camera(local, velocity, agl)`: same cover, re-centering (and `origin_shifted`), fades and jobs.
- Invalid input (any non-finite value, \|lat\| > 90, \|lon\| > 180) is logged as a warning and ignored: no state change, no shift.

### 3.4 Signals [0.7]

Emitted on the main thread from inside the call that causes them (never from worker threads). Handlers may call back into the node.

| Signal | Since | Emitted |
|---|---|---|
| signal `origin_shifted(shift: Vector3)` | 0.7 | During `update_camera` / `update_camera_geodetic` when the origin is re-centered. `shift` = `(dx, 0, dz)` local meters, the same vector the next `take_origin_shift()` returns (the signal does not consume it). Subtract it from every node kept in local space (aircraft, markers, particles); the tile host keeps using `take_origin_shift`. |
| signal `status_changed(status: Dictionary)` | 0.7 | During `update_camera` / `update_camera_geodetic` / `poll_ready` when the `state` or `message` of `status()` differs from the last emitted one (not for counter-only changes). Same Dictionary as `status()`. Not emitted by `configure_world` or `shutdown` themselves; the first update after them reports the change. |

### 3.5 Status [0.7]

`status()` and `status_changed` carry:

| Key | Type | Meaning |
|---|---|---|
| `state` | String | `ok`, `degraded`, `offline` or `error` (rules below) |
| `message` | String | Short summary, stable per situation (the details are in `last_error`). Empty when ok and running; `not configured` before configure, `shut down` after `shutdown()` (both with state `ok`) |
| `failed_fetches` | int | Failed tile fetches since the last configure (cumulative; every retry counts) |
| `last_error` | String | The latest fetch, decode or configuration error since the last configure (empty if none) |
| `terrain_active` | bool | **[1.6]** The terrain is active in this configuration (the host requested the layer `terrain` **and** the profile has `terrain.enabled`); false before configure, after `shutdown()` and for a world that failed to start. The host reads it instead of re-deriving the rule from `world_profile()`, whose `terrain.enabled` can be true for a flat world. Not part of the `status_changed` change test. |

Rules (first match wins), derived from the fetch results the library already tracks:

1. **error**: a configuration problem that retrying cannot fix: the archive does not match the tileset contract (section 3.1), or the workers could not start. Message = that error. Sticky until the next configure.
2. **offline**: the archive cannot be opened (server unreachable or not serving the file) and no tile has been served in this configuration, neither from the network nor from the disk cache. Message `tile server unreachable and no cached tiles`.
3. **degraded**: the archive cannot be opened but cached tiles are being served (`tile server unreachable; showing cached tiles only`), or the disk cache was turned off for this configuration after three consecutive failed writes (disk full, I/O error; `disk cache disabled after write failures; streaming without it`, sticky until the next configure; tiles keep streaming from the network), or any tile fetch or decode failed within the last `streaming.retry_max_s` + 5 s (35 s by default; `some tiles failed to load; retrying`). The messages are checked in that order.
4. **ok** otherwise. The synthetic city is always ok.

Hosts should treat unknown states as `degraded` and ignore unknown keys (additive).

### 3.6 World seed [1.7]

A world configured with `seed_world` (section 3.1) generates every vector tile from the seed files (`docs/spec-world-seed.md`; phase S1: water and countryside ground in all four bands, airports; cities come in later phases and are not drawn yet). Every z13 tile (and so every finer tile) is routed to the generator. Output goes through the normal tile path: the ready-tile dictionary, the cover, guarantees, fades and visibility rule are unchanged; the generated ground uses the encodings of section 9 (class 7 `aeroway` and the tint), airports add buildings (terminal `transportation` = civic, hangars `hangar` = industrial, tower `office` with a tagged height; ids in the OSM way-id space above 2^40) and `airport_lights` (section 8). Same files and profile = same tiles on every run and machine (section 11). `status()` of a seed world is `ok` (the generator never fails; no tile server).

**`airports()` entries** (sorted by ident; only airports with an open runway; local positions in the current frame, `y` = `ground_height_at` there):

| Key | Type | Meaning |
|---|---|---|
| `ident`, `name`, `type` | String | From the airport file (`type`: `large_airport`, `medium_airport`, `small_airport`) |
| `lat`, `lon`, `position` | float, float, Vector3 | Reference point |
| `elevation_ft` | float or nil | From the file; informational only (the terrain decides every height) |
| `runways` | Array[Dictionary] | Sorted by `designator` |

Runway keys: `designator` (`"08/26"`), `le` / `he` (Dictionary per end: `ident`, `lat`, `lon`, `position` (physical end), `threshold_lat`, `threshold_lon`, `threshold_position` (landing threshold, displaced thresholds applied), `displaced_threshold_m`, `touchdown_position` (aiming point 300 m past the threshold, at most a quarter of the landing distance), `heading_deg` (true heading of a landing on this end)), `length_m`, `width_m`, `surface` (file text), `paved` (bool), `lighted` (bool), `approximate` (bool: an end was missing in the file, the runway is centred on the reference point along its heading), `lights` (PackedVector3Array: the runway's lights, `y` = ground + `seed.airport.lights.height_m`; the tiles draw the same points on the drawn ground, i.e. up to the runway's stacking offset higher, section 9 "Airports"), `light_colors` (PackedColorArray). Runway markings are the host's (decals from the ends); the ground mesh has no UV.

**`seed_world_info()` keys:** `manifest` (String), `generator_version` (int; changes with every intended output change), `phases` (PackedStringArray of the built phases of the spec's section 11, today `["S0", "S1"]`; a host self-test runs the checks of these phases only), `world_version` (int, the author's), `world_seed` (String), `cities` (Array of Dictionary: `id`, `name`, `lat`, `lon`, `radius_km`, `version`, `source` (`"synthetic"`; later `"real:<url>"`), `airports` (PackedStringArray)), `airports` (int), `water_polygons` (int), `warnings` (PackedStringArray: load-time validation warnings, also logged once), `memory` (Dictionary: `water_index_mb`, `water_raster_mb`, `strip_index_kb`, `airports_kb`, `load_ms`; display only).

## 5. LOD cover, guarantees and visibility rule [0.5]

**Cover (default values; tunable through the world profile `bands`, `buildings`, `ground` since 0.6).** Rust selects tiles as a quadtree cover by 3D slant distance `d = √(horizontal² + (cam_alt − ground)²)` to the nearest point of the tile box (footprint × the tile's max building height; **[1.4]** with the terrain active the box is `[h_min, h_max + building height]`, `h_min`/`h_max` = the terrain's minimum / maximum over the tile from a fixed 9 × 9 sample grid padded by half the largest neighbour difference, a pure function of the key; `cam_alt` = the camera's MSL altitude (AGL + terrain under the camera) moved by the look-ahead, never below the terrain under the look-ahead point; root candidates are bounded by the highest possible terrain + 400 m):

| Band | ring | Zoom | Slant distance | Buildings | Ground | Lights |
|---|---|---|---|---|---|---|
| R0 | 0 | 16 | < 0.6 km | full extrusion, DP 0.5 m | all roads and areas | none (windows) |
| R1 | 1 | 15 | 0.6–2.5 km | extrusion, DP 2 m, drop < 20 m² | no minor paths, drop areas < 200 m² | none (windows) |
| R2 | 2 | 14 | 2.5–7 km | merged coarse blocks, DP 4 m, drop < 50 m² | no class-6 roads, drop areas < 2500 m² | yes |
| R3 | 3 | 13 | 7–25 km | none | **[1.3]** coarse: secondary and more important roads, drop areas < 40000 m² (was none) | yes |
| — | — | — | > 25 km | nothing requested | | |

Each location is shown by the band its slant distance falls in; candidates lie within horizontal radius `√(25 km² − h²)` of the look-ahead point (`h` = camera height). Look-ahead point per band = camera + velocity × 20 s (vertical speed included), offset clamped to half the band's radius. Work (fetch and mesh jobs) is ordered like the deliveries (guarantee 5: nearest to the camera first; **[1.5]** before: finer band first, then slant distance to the look-ahead point), with at most 4 fetches and 2 mesh jobs in flight per band. Hysteresis: a tile changes band only once its slant distance is 15 % past the band edge (z13 roots are added below 25 km and dropped beyond 28.75 km). Bands are chosen by slant distance only; there are no altitude rules, and the host has none either. Coarsening is bottom-up, so the two sides of any swap differ by exactly one zoom level.

**Guarantees from Rust [0.5]:**

1. Refining always requests all 4 children of a tile as one sibling group.
2. Every requested tile is delivered through `poll_ready`, even when empty (empty `mesh`/`ground` Arrays, empty `lights`), so sibling groups always complete.
3. **Refine:** a parent is unloaded only after all 4 of its children have been delivered **and** the swap fade (section 6) has completed. The fade starts in the `poll_ready` call that delivers the last child; the parent is unloaded in the frame its final 0.0 is reported. **[1.5] First fill:** a parent that was delivered while the cover already wanted its children (a *stand-in*: after `configure_world` / a teleport, or flying into a region nothing was loaded for, every level on the way down to the band of the camera's distance) has no swap fade: it is unloaded in the `poll_unload` of the frame whose `poll_ready` delivered its last child, and neither it nor its children appear in `poll_fades` for that swap. A parent that was a leaf when it was delivered (it had been showing as the final detail) fades, unless `fades.max_active` swaps are already fading (**[1.7]**, section 6): then it is unloaded at once like a stand-in.
4. **Coarsen:** the parent is delivered again, fades in while its children fade out, and the children are unloaded (in one `poll_unload` batch) in the frame the fade completes (**[1.7]** or, with `fades.max_active` swaps already fading, in the frame the parent is delivered, without a fade). While this happens, the children's subtree is frozen (no new requests or deliveries in it).
5. Delivery order: a tile is handed out only when its parent is covered (present, with its own sibling group present up to the root) and its parent is not in a fade, so a new sibling group never overlaps a visible coarser tile and every tile takes part in at most one fade at a time (a first-fill swap, guarantee 3, is no fade, so it never holds the next level back). **[1.5]** Among the tiles that may be handed out, fresh tiles go before re-deliveries, then strictly by slant distance from the **camera** (no look-ahead) to the tile's sibling group (the parent's box, i.e. the nearest of the 4 siblings, since a tile shows only once its whole group is uploaded; a root's own box), then the tile's own distance; ring and key only break ties. Bands are not ranked against each other (before 1.5: finer band first, then distance to the band's look-ahead point), so a first fill grows outward from the camera, each location going root → finest band within a few frames.
6. **No-fade exceptions:** a z13 root leaving the cover takes its whole subtree in one `poll_unload` batch with no fade; a coarsening parent that is still uploaded while its child group is incomplete (children not visible) needs no fade, and the subtree is unloaded at once; **[1.5]** a first-fill stand-in is swapped for its children at once (guarantee 3).

**Visibility rule (evaluated by the host, locally from keys) [0.5]:**

- A tile is *present* if it is uploaded, or all 4 of its children are present (recursive).
- A tile without a `poll_fades` entry is visible iff it is uploaded, **and** (z == 13 or all 4 of its siblings are present), **and** not all 4 of its children are present.
- A tile that has a `poll_fades` entry is visible whenever it is uploaded, regardless of the sibling/children clauses (both sides of a swap show at once).
- New tiles stay hidden until `poll_fades` has run once after their upload, so the shader `fade` is set before the first visible frame.
- The host never hides tiles any other way (no distance or altitude culling of its own); the coarser tile stays until Rust unloads it.
- The ground mesh and the light sprites of a key follow the same visibility as its building mesh.

**[1.5] Per layer.** The cover, guarantees 1–6, the visibility rule and the fades (section 6) hold **per layer**; the two layers are independent quadtrees and never share a key. For the terrain layer read the root zoom `terrain.far_zoom` (default 10) where the rules above say z13 and `terrain.near_zoom` (default 14) for the finest zoom; its bands are `terrain.bands[i].edge_m` (default T0 z14 < 2.5 km, T1 z13 < 7 km, T2 z12 < 25 km, T3 z11 < 60 km, T4 z10 < 130 km), with the same hysteresis, look-ahead and fade rules from `bands.*` and `fades.cap_s`; `terrain.max_fetch` / `terrain.max_mesh` jobs per ring; the box of a terrain tile is its terrain range (`Terrain` 9 × 9 grid, as for vector tiles, without a building height). Terrain tiles that cannot be seen are not requested: **horizon cull** (`terrain.horizon_cull`, default on), a terrain tile is out of the cover when the horizontal distance from the band's look-ahead point to its nearest point exceeds `√(2R·max(h_cam − h_ref, 0)) + √(2R·max(h_max − h_ref, 0)) + terrain.horizon_margin_m` (`R` = 6 371 km, `h_cam` = look-ahead altitude MSL, `h_max` = the tile's box top, `h_ref` = the lower of the ground under the look-ahead point and the tile's box bottom), with the band hysteresis (a tile in the cover leaves only 15 % past the line, comes back at the line). It applies to roots and to **whole sibling groups** (a node splits only while at least one of its 4 children is above the horizon; a split node keeps all 4), so the sibling-swap rule is unchanged. It assumes a real-size Earth: a host drawing a stronger visual curvature turns it off or widens the margin. The vector layer is not culled. A terrain host evaluates the visibility rule for the terrain keys exactly as for the vector keys, in its own tile map.

**[1.5] Delivery order across layers:** `poll_ready` merges both layers into one order, the order of guarantee 5: fresh tiles before re-deliveries, then strictly by the slant distance from the camera (sibling group, then own), with no weight between the layers (ties go to the vector world). Both layers share `max` and the per-frame re-delivery limit, and their mesh jobs share one worker queue in the same order. (The first 1.5 draft counted a terrain tile at half its distance and kept "finer band first" within a layer.)

History: this replaces the M3 `quadrants` ready-tile key, which no longer exists. The first M4 draft of the rule said "uploaded" where it now says "present" and left holes once one sibling was refined.

## 6. Dithered LOD fades [0.5]

A sibling swap (parent ↔ its 4 children, either direction) is not instant: both sides exist together while `fade` ramps. Rust adds no geometry.

- `fade` = the tile's visible fraction (0..1). The incoming side goes 0→1, the outgoing side 1→0, and the two always **sum to exactly 1** (values are quantized to 1/256, so `f` and `1 − f` are exact in f32).
- `fade` is driven by slant distance, not time: it ramps across the band's hysteresis gap (15 % of the finer band's edge), so hovering freezes a transition. It only moves forward; if the split decision flips mid-fade, the fade reverses from its current value (no pop). Rust force-completes any transition `fades.cap_s` after it started (safety cap; default **0.75 s** since profile_version 2, 3 s before). A fade that has not reached its end by distance within the cap is cut short: the swap completes in one frame. At 250 m/s the overlap is ~0.5 s.
- **[1.7] Concurrency cap:** at most `fades.max_active` swaps (default 4; a swap = the coarse tile and its 4 children) fade at the same time, vector and terrain layer together. The host's dither variant discards pixels, which turns off hidden surface removal on tile-based GPUs (Apple), so the number of dithered meshes is bounded. A swap that finds the cap reached starts no transition and completes at once, like a first-fill swap: a refine unloads the parent in the `poll_unload` of the frame whose `poll_ready` delivered the last child; a coarsen unloads the children in the `poll_unload` of the frame whose `poll_ready` re-delivered the parent. Neither side appears in `poll_fades` for that swap. Swaps take free slots in delivery order (nearest group first). `0` turns every fade off. A host that treats absent keys as fade 1 needs no change.
- `poll_fades()` returns key → float for **every** tile currently in a transition, changed or not, so the host may replace its whole map each call. A tile not in the dictionary has fade 1.
- Incoming tiles get one last entry with 1.0 on the call where they finish; that call is also where the host drops the entry. Outgoing tiles get a last entry with 0.0 and are sent through `poll_unload` in the same frame.
- A tile delivered by `poll_ready` that starts a transition is already in the next `poll_fades` result with its starting value (0.0 for incoming).
- **[1.5] First fill:** a tile delivered over nothing (a root) or over a first-fill stand-in (section 5, guarantee 3) starts no transition: it is not in `poll_fades` (fade 1, visible as soon as its sibling group is complete), and the stand-in leaves through `poll_unload` in the same frame, also without an entry. So after a teleport `poll_fades` stays empty until the first real detail change. Fades remain for every change of detail of a tile that had been showing as the final detail (refine of a leaf, every coarsen). A host that treats absent keys as fade 1 (this section) needs no change.

**[1.5]** Terrain keys (`t/z/x/y`) appear in `poll_fades` for terrain swaps with the same rules; a terrain host applies the dither rule to the terrain mesh too (`fade_parity` = `z & 1` of the terrain key's zoom).

**Dither rule (host shader; buildings and ground, never light sprites):** per mesh instance, uniform `fade` (float) and `fade_parity` = `z & 1` of the tile key (the two sides of a swap differ by one zoom, so their parity differs). Screen-pixel pattern `p` in [0,1) from a 4×4 Bayer matrix of `FRAGCOORD.xy`. Parity 0 keeps a pixel when `p < fade`; parity 1 keeps it when `p >= 1.0 - fade`. With fade_in + fade_out = 1 the two sides cover complementary pixels. At `fade == 1` the shader skips the test (no discard), so opaque tiles keep early depth rejection.

## 7. Building mesh [0.5]

One merged mesh per R0–R2 tile (one draw call). Buildings that cross tile edges are clipped exactly to the tile rectangle; a tile's 4 children cover exactly the same geometry as the tile itself (no doubles, no holes across a swap). Walls are flat-shaded quads with outward normals; roofs are flat earcut polygons with holes, normal +Y. A raised part (`min_height` > 0.25 m) also gets a bottom cap with normal −Y. Building bases stand on the terrain (lift 0). **[1.4]** With the terrain active the base is the **lowest** terrain height under the building's outer-ring vertices (as decoded, before clipping and simplification), so a building on a slope stands on its lowest corner; roof height stays relative to the base (COLOR `a` unchanged). Every wall of a part standing on the ground (`min_height` ≤ 0.25 m) gets a **foundation**: a quad under the wall from `base − foundation(band)` up to the base (**[1.7]** a fixed table, section 9 "Drape table": R0 3 m, R1 7 m, R2 17 m), normal = the wall's, `TEX_UV` `u = −1` and `v` = meters from `−foundation(band)` to 0, so it carries no windows; walls keep `v = 0` at the true base. No foundation with the terrain off (output unchanged).

**[1.7] Per-vertex walls** (replaces the 1.4 base and foundation rule above while the terrain is active; flat output unchanged): the base is the **highest** terrain height under the footprint as decoded (every outer-ring vertex, points along every outer edge at most 10 m apart, the centroid when it lies inside, and the points of a global Mercator lattice of about 11 m inside the footprint, at most 64 per building), so the roof (`base + height`), the window floors and the light point (section 8) are the same in every band and tile. Every wall of a part standing on the ground reaches down to the **exact ground at each of its vertices** (never above the base); a wall edge longer than `terrain.drape_step_m` is split at midpoints while the ground along it falls more than the band's drape margin (at least 0.1 m) under the straight line, so the bottom follows a valley. Under each wall quad a windowless **foundation** quad continues `foundation(band)` further down. `TEX_UV`: a windowed wall keeps `v = floors` at the roof and the same floor height all the way down, so `v` at a bottom is `floors − (roof − y) / floor_h` and goes **negative below the nominal bottom** (more window rows on the downhill side; the host's `floor(v)` handles it); windowless walls and foundations have `u = −1` and `v = y − (base + min_height)` in meters (negative below). A raised part (`min_height` > 0.25 m) whose centroid lies in the footprint of a ground-standing building takes that building's base (the highest if several), so it stays `min_height` above it. Buildings with a footprint below `buildings.rN.min_area_m2` or **[profile 2]** a resolved roof height below `buildings.rN.min_height_m` (section 3.2) are left out of band N's mesh.

**Vertex COLOR:**

| Channel | Meaning |
|---|---|
| `r` | light profile id / 8: 0 residential, 1 office, 2 retail, 3 industrial, 4 civic, **[1.0]** 6 landmark, 7 dark. Id 5 ("unknown") is reserved: unknown kinds are resolved (section 3.2) before encoding, so the mesh only carries 0–4, 6 and 7. |
| `g` | seed 0..1, a stable hash of the OSM id and type (for lit windows). Rust computes it with 24-bit resolution, but **the host does not see 24 bits**: Godot stores vertex COLOR as 8 bits per channel (RGBA8), so the shader reads `g` quantized to 1/255. The window shader therefore builds its hash seed from the 8-bit values of `g`, `b` and `a` together (24 bits, not a 24-bit-exact seed). Determinism holds because the same tile gives the same bytes; two buildings with the same `g`, `b` and `a` bytes share a window pattern (accepted). |
| `b` | floor-to-floor height / 10 m (clamped 0..1; typically 2.5–5 m) |
| `a` | building roof height / 400 m (clamped 0..1) |

**TEX_UV [1.0]:**

- **Windowed walls** (the building's profile has a `windows` block, it is not tagged `windows=no`, the band is R0 or R1, and the wall part `height − min_height` is at least `buildings.min_window_wall_m`): `u` in **window columns**, `v` in **floors**.
  - Each ring (outer ring and each hole) is split into **runs** at its corners: a vertex where the outline turns by more than 35°, or by more than 20° with both adjacent edges at least 2 × `width_m` long (so a round tower of many short edges is one run and a rectangle is four). Interior clip-seam edges (a building cut at the tile edge) carry no wall and also end a run. A ring without corners is one run.
  - A run of length `L` holds `count = round(L / width_m)` columns of width `L / count` (0.67–2 × `width_m`); `u` runs from `column_base` to `column_base + count`, so every run **starts and ends on an integer** and a window never wraps a corner. `column_base` starts at 0 for each polygon and carries on across its runs and rings (outer ring, then holes), so `floor(u)` is a column id unique within the polygon (a raised part or multipolygon part starts again at 0).
  - `v` counts floors from the bottom of the extrusion (the part's `min_height`): `floors = max(1, round(wall_h / floor_h))` with `floor_h` = COLOR `b` × 10 m before quantization, and the floors are stretched to fill the wall, so the top of the wall is exactly `v = floors` (no partial top row).
  - The host's cell is `floor(UV)` (column, floor) and the position inside it `fract(UV)`.
- **Windowless walls**: `u = -1` on all four vertices and `v` = **meters** up from the bottom of the extrusion. Windowless are the walls of a profile without `windows` (industrial, landmark, dark), of a building tagged `windows=no`, of a wall part lower than `buildings.min_window_wall_m`, a run shorter than half a window (`count = 0`), and **every R2 wall** (R2 has light sprites; coarse blocks carry no grid).
- Wall UVs are per wall quad; the grid may shift slightly at tile seams (a building clipped at a tile edge counts its columns per piece) and between R0 and R1 (different simplification).
- **Roofs and bottom caps** (normal ±Y): `(x, z)` of the vertex in tile-local meters (relative to `origin`), not world meters; unchanged. A bottom cap (normal −Y) usually has `u ≥ 0`, so a host must test `abs(NORMAL.y) > 0.7`, not `u`, to exclude caps from the window grid.

## 8. Lights [0.5]

- `lights` / `light_colors` are filled for the bands `lights.min_ring`..R3 only (profile 3; default **1 since profile version 4 [1.0]**, was 2: R1, R2 and R3; empty for R0, which has windows only). R1 tiles carry both a window mesh and sprites: the host cross-fades them over a view-depth range (the building shader's averaged window glow fades out while the sprites fade in, `WorldRenderSettings.WindowSpriteBlendStartM`/`EndM`, default 900..2000 m), so R1 buildings are lit by windows up close and by sprites beyond, never both at full strength. `min_ring` = 2 restores sprites on R2/R3 only (R1 windows then fade to nothing with no sprites), 0 adds sprites to R0. The fade sum rule below holds for sprites of every band. Light points come from every owned building of the tile, independent of the building-mesh filters `min_area_m2` / `min_height_m` (a building left out of the R2 mesh still has its light).
- One light per building at its footprint centroid and roof height (a building split across tiles counts once). **[1.0]** Buildings of the `dark` profile (section 3.2) have no light point (they are left out of single lights and clusters alike); `landmark` buildings have one in the landmark color (their floodlight), so a building dark or floodlit up close is the same from afar.
- `light_colors`: rgb = average color of the lights in the point, a = intensity weight `clamp(sqrt(count) / 8, 0.125, 1)`; a single light has count 1 (a = 0.125). Colors by profile (informative): residential warm 2700 K, office cool 4500 K, retail bright white, industrial sodium, civic warm ~3000 K, **[1.0]** landmark warm floodlight ~3000 K.
- **[1.1] Street lamps** (`street_lights` / `street_light_colors`, profile `lights.street`): a point every `spacing_m` (35 m) along the centerline of each lit road, starting half a spacing from the line start, `height_m` (9 m) above the ground; only points inside the tile rectangle, so a road crossing a seam is lit once. A road is lit when it carries a `lit` tag (`ground.roads.lit_values`) or its class is `untagged_max_class` (5 = residential) or more important; 0 = tagged roads only. Bands `lights.street.min_ring`..R3 (default 0: every band, R0 included); `min_ring` 4 = none. R3 (z13) archive tiles hold major roads only, so R3 lamps line motorway .. secondary roads. rgb = `lights.street.color` (sodium orange) or, on `alt_share` (0.3) of the roads, `lights.street.alt_color` (white LED); the lamp type is chosen per road from its OSM id, so a road has one lamp type in every tile and band it crosses. a = `intensity(count)` like building lights (a cluster averages the colors in its cell). In light-carpet mode (below) they are clustered into the same cells, as their own set (they keep their color). Street lamps are **not** cross-faded with windows: a host draws them at every distance. A host written for 1.0 ignores the two keys.
- **[1.2] Beacons** (`beacon_lights` / `beacon_light_colors`, profile `lights.beacons`): aircraft warning lights placed from **geometry alone** (never tags), so a synthesised city gets them by the same rule. Every owned building whose resolved roof height (the height the mesher extrudes to, section 7) is at least `min_height_m` (60 m) gets beacons 0.5 m above its roof at the corners of its outer ring (the extreme vertices along the four diagonals, pulled 0.5 m inwards, closer than 2 m merged), or one in the middle when the footprint is narrower than `corner_min_size_m` (15 m) along either axis; plus the same points every `level_spacing_m` (45 m) up the facade while at least half a spacing below the roof (0 = roof only). rgb = `lights.beacons.color` (red) or, on `alt_share` (0.15) of the beacon buildings by OSM id, `alt_color` (green); **a = blink phase** 0..1, one per building (its beacons flash together; the host owns the blink rhythm). Never clustered (the light-carpet mode does not change them). Bands `lights.beacons.min_ring`..R3 (default 0 = every band, so a tower is marked from 25 km); 4 = none. A host written for 1.0 / 1.1 ignores the keys.
- **[1.7] Airport lights** (`airport_lights` / `airport_light_colors`, seed world only, profile `seed.airport.lights`): for each runway marked `lighted` in the airport file: edge lights every `edge_spacing_m` (60 m) on both edges 1.5 m outside the pavement, end to end (white), threshold lights across the runway every ~3 m at each landing threshold (green), end lights across the runway 3 m past each physical end (red), and on paved runways of at least `approach_min_runway_m` (1200 m) an approach row on the extended centreline before each threshold, `approach_length_m` (900 m) long, one every `approach_spacing_m` (30 m) (white); taxiway edge lights every `taxiway_spacing_m` (60 m) on medium and large airports (blue). `y` = terrain + the weighted drape lift (0 inside the fence, section 9 "Airports") + the stacking level × step of the surface they stand on (runway 3, taxiway 2; approach rows 7, the highest area level outside a fence) + `height_m` (0.5 m), so the lights sit on the runway as drawn in every band. Every band (R0..R3), only the points inside the tile rectangle; never clustered and not part of the light-mode re-delivery; always on (no lit share: the host shows them at night). A host written for 1.6 ignores the keys.
- **Light carpet:** above ~3000 m AGL (on at 3300 m, off below 2700 m) each tile's lights are clustered into 100 m cells (mean position, mean roof height, average color, `count` = lights in the cell). On every mode switch Rust re-delivers already-uploaded lit tiles (bands >= the smallest of `lights.min_ring`, `lights.street.min_ring` **[1.1]** and `lights.beacons.min_ring` **[1.2]**) under the same key with the other light set (and the same mesh and ground); the host re-uploads in place. Re-deliveries are limited to 1 per frame.

## 9. Ground [0.5]

One flat ground mesh per tile (R0–R2; **[1.3]** R3 too): landuse/park/water areas plus buffered road strips, relative to `origin`, clipped to the tile, same sibling-swap visibility as the building mesh. NORMAL = +Y; triangles clockwise seen from above; no TEX_UV (until imagery, planned 1.7). **[1.3]** The R3 ground (`ground.r3`) is coarse, so a far tile is never see-through while its R2 children load: DP 20 m for areas and 15 m for roads, areas under 40000 m² dropped, roads of class 3 (secondary) and more important only (the archive holds major roads only at z13 anyway). Light-mode re-deliveries of R3 tiles carry the same ground again (section 8).

**Ground COLOR (exact multiples):**

| Channel | Meaning |
|---|---|
| `r` | class / 16: 0 grass/park, 1 forest, 2 water, 3 residential, 4 commercial, 5 industrial, 6 other landuse, **[1.7]** 7 aeroway (seed world airports), 8 road |
| `g` | lit: 1 for lit roads (`lit` = yes, 24/7, automatic, sunset-sunrise, dusk-dawn, limited, interval, night), else 0; areas: **[1.7]** tint / 8 (0..7: the patchwork of a seed world's countryside, so farmland and meadow, both class 0, differ; the shader shifts hue / brightness by it), 0 for every archive or synthetic-city area |
| `b` | road class / 8; areas: 0, **[1.7]** except class 7: sub-kind / 8 = 0 airfield (the grass inside the fence), 1 runway paved, 2 runway grass, 3 taxiway, 4 apron (and car park) |
| `a` | 1 |

**[1.7] Class 7 and old hosts.** A host without a class 7 branch draws it in its unknown-class colour (the 1.6 addon: pale green). A host that cannot update sets the profile's `seed.aeroway_class` to 6: airport areas are then class 6 with the same sub-kind in `b`.

**[1.7] Seed world ground** (all four bands, R3 under `ground.r3`): countryside patches (`forest` class 1 level 6, `farmland` / `meadow` class 0 level 5, through `ground.areas`) on the z15 grid with warped edges and a tint each; water areas (class 2, level 7) from the water file's polygons (sea, lakes, rivers); per airport the fence as class 7 sub-kind 0 at level 1, taxiways and aprons at level 2, runways at level 3 (seed generator 2; generator 1 used 8 / 9 / 10). The fence rectangle is cut out of every countryside and water area of the tile (exactly, along its edges: "airports cut water"), so inside a fence only these three levels stack, directly on the levelled strip height (section 9 "Airports"); no road enters a fence in phase S1. Water areas drape like any area (section 9 Drape); the terrain's water rule makes the sea and lakes flat, so they lie flat on it; rivers follow the relief.

**Road classes** (`b` × 8) and full strip widths: 1 motorway (14 m), 2 trunk + primary (10 m), 3 secondary (8 m), 4 tertiary (6 m), 5 residential + unclassified + living_street (6 m), 6 everything else (service, pedestrian, footway, path, cycleway, track, steps, …; 3 m). `_link` roads keep their class at 60 % width (min 3 m). R0 has all roads; R1 drops minor paths (footway, path, cycleway, steps, bridleway, track, corridor, elevator, via_ferrata, escalator); R2 drops class 6; **[1.3]** R3 keeps classes 1–3.

**Area classes** from the `landuse` layer `kind`: grass/park = park, garden, playground, pitch, golf_course, recreation_ground, nature_reserve, grass, meadow, grassland, scrub, heath, wetland, village_green, cemetery, allotments, orchard, vineyard, farmland, plant_nursery, flowerbed; forest = forest, wood; water = water, riverbank, reservoir, basin, salt_pond; residential; commercial = commercial, retail; industrial = industrial, railway, port, depot, garages, quarry, landfill; other = any other kind. R1/R2/R3 drop areas under 200 / 2500 / 40000 m².

**Heights:** ground y = terrain height + a small lift per stacking level against z-fighting. Levels bottom to top: nature_reserve, other landuse, residential, industrial, commercial, grass/park, forest, water, then roads from class 6 up to motorway. Lift = level × 0.02 m (R0), 0.06 m (R1), 0.15 m (R2), 0.5 m (R3); at most ~2 m at R2 and ~6.5 m at R3 (seen from 7 km or more). All Rust heights (building bases, light points, ground vertices, the slant-distance boxes, `ground_height_at`) come from one terrain function, carried explicitly by every job and by the cover; 0 with the terrain off.

**Drape [1.4]** (terrain active): ground y = terrain height + `lift(band)` + level × step. **Drape table [1.7]:** `lift(band N)` (the drape margin) and the foundation depth (section 7) are a fixed table of the library, not derived from the profile: lift R0 0.125 m, R1 0.375 m, R2 1 m, R3 2.5 m; foundation R0 3 m, R1 7 m, R2 17 m, R3 41 m. They are the values the 1.4 lift rule gave with the default profile (largest `max_error_m` of the terrain bands within reach of `rN_edge_m × hysteresis`, R0 1 m, R1 3 m, R2 8 m, R3 20 m at `detail_scale_max` 2; margin = a quarter of it at detail 1, foundation = 2 × it + 1 m); overriding `terrain.bands`, `terrain.detail_scale_max` or `bands.*` no longer changes them (the terrain bands and the vector band edges are being replaced by screen-space error, `docs/spec-terrain.md` "Design change: drape frozen"). Area and road edges longer than `terrain.drape_step_m` (25 m) are subdivided where the terrain along them (tested at 1/4, 1/2 and 3/4) rises more than the band's drape margin (at least 0.1 m) above the straight edge or falls more than twice it below (area triangles split at edge midpoints, decided per edge so neighbouring triangles agree; roads along their centerline; a road strip is flat across its width). A triangle whose edges are all shorter than `drape_step_m` is not split, so on a strongly concave height (e.g. the outer half of an airport shoulder) its interior can sag a few centimetres under `ground_height_at` (measured 1.3 cm in R0 at EYVI). **Water** areas (class 2) drape like every other area (plain terrain height + lift, subdivided to `drape_step_m`, so no water vertex is under the terrain mesh); only with `terrain.water_snap_m` > 0 (default 0) are water areas not subdivided and each water vertex takes the minimum terrain height in a 5 × 5 window of half-width `water_snap_m` around it (per vertex, so a vertex on a tile seam has the same height in both tiles; for a height function with flat lakes of its own, e.g. a DEM). Bridges and tunnels: the archive has no bridge/tunnel attribute, so every road drapes on the terrain. Light points: a building's light is at its base + roof height (clusters: the mean of their members); street lamps `height_m` above the terrain at their point.

**[1.7] Airports (seed world; seed generator 2).** Inside an airport fence the ground has **no drape lift**: the drawn runway, taxiways, aprons and fence grass lie at `ground_height_at` + level × `ground.rN.lift_step_m`, so a game that rolls on `ground_height_at` touches the pavement as drawn (landing physics, AGL). The terrain mesh is exact there (section 9a), so only the stacking step separates the surfaces. **Lift weight rule** (continuous, no step): the drape lift of a vertex is `lift(band) × k`, where `k` is the strip rule's own blend weight: 0 inside a fence, `smoothstep(0, seed.airport.shoulder_m, d)` at distance `d` outside it (the shoulder over which the height function blends back into the relief), 1 beyond the shoulder and everywhere in a non-seed world. Draped edges in a fence are subdivided until they follow the height function to `max(1 cm, step / 2)`; in the shoulder to `lift × k / 4` + half the feature's stacking offset (at least 0.1 m). Within 30 m of a runway's physical end the fence plane has a kink (the strip height is constant past the ends, the slope change is at most `max_slope`), where an edge of up to `drape_step_m` adds up to about 6 cm. **Residual** (drawn surface − `ground_height_at`, default profile, measured on all 37 runways of the two-cities test world (28 airports) at 20 centreline points and 45 points across each strip):

| Surface | Level | R0 | R1 | R2 | R3 |
|---|---|---|---|---|---|
| Runway | 3 | 0.06 m | 0.18 m | 0.45 m | 1.5 m |
| Taxiway, apron | 2 | 0.04 m | 0.12 m | 0.30 m | 1.0 m |
| Fence grass | 1 | 0.02 m | 0.06 m | 0.15 m | 0.5 m |
| Tolerance (planar part) | | ±0.01 m | ±0.03 m | ±0.075 m | ±0.25 m |

The stacking step stays: a runway coplanar with the fence grass and the terrain mesh would z-fight. The host's ground shader depth bias (`depth_bias_per_m`) works on top of it. Small runways whose area falls under `ground.rN.min_area_m2` (R3) show the fence level instead. Airport lights follow the same rule (section 8). **Host:** anything the host places on the drawn runway (marking decals, a touchdown check) uses `ground_height_at` + 3 × `ground.rN.lift_step_m` for the runway band N, with **no** terrain error term. A library with `seed_world_info()["generator_version"]` 1 still drew the runway at `lift(band)` + 10 × step (the old replay: 1.2 / 3.6 / 9.5 / 25 m). Generator ≥ 2 uses this rule.

## 9a. Terrain mesh [1.5]

Delivered only to a host that requested the layer `terrain` with a profile that enables it (section 3.1). One mesh per terrain tile (key `t/z/x/y`, `ring` = index in `terrain.bands`), one draw call.

- **Surface:** a TIN (greedy insertion, Garland–Heckbert / Delatin, deterministic) over the tile's heights sampled on a regular grid of the procedural terrain (z14 64, z13 128, z12 and coarser 256 cells per side; about 22 m at z12–z14 at 55° N): points are inserted until the largest vertical error is at most `bands[ring].max_error_m × detail` (`set_terrain_detail`, default 1) or another insertion could exceed `bands[ring].max_triangles` (surface triangles; skirts come on top). The four corners are always vertices; with `bands[ring].max_edge_m > 0` the TIN starts from a regular seed grid of `⌈tile width / max_edge_m⌉ + 1` points per side (corners included; fewer if they would exceed `max_triangles`) so the host's visual earth curvature bends flat tiles. Every vertex lies on the tile (edges included, nothing outside): neighbours sample the same lattice, so shared edge samples are identical, and the edge polylines of two neighbours differ by at most twice the error.
- **Skirt:** every hull vertex gets a copy `terrain.skirt_m` lower (0 = automatic: `2 × max_error_m × detail + 1` m, at most 60 m; **[1.7]** with `max_error_m` the larger of the tile's band and the next coarser band, because a sunk edge lies up to twice the error under the height function), each hull edge is closed by a vertical quad facing outwards (away from the tile centre); it hides the cracks between neighbours and across bands.
- **Arrays** (`Mesh.ARRAY_MAX` layout): `VERTEX` (PackedVector3Array, metres relative to `origin` = tile centre, the same projection as the vector tiles: x east, y = height above MSL, z −north) and `INDEX` (PackedInt32Array): surface triangles first, clockwise seen from above (Godot front face), then the skirt quads (2 triangles each). `NORMAL` only with `terrain.shading = "smooth"` (area-weighted vertex normals; skirt vertices copy their top vertex's); otherwise the host shades flat from screen-space derivatives. No COLOR, no TEX_UV; every other slot nil. **[1.7]** In a seed world every vertex also has **COLOR**: `r` = ground class / **8** (2 water incl. rivers, 7 = `seed.aeroway_class` inside an airport fence, else the countryside patch's class: 1 forest, 0 grass), `g` = the patch's tint / 8 (0 for water and airfields), `b` = 0, `a` = 1; skirt vertices copy their top vertex. The class comes from the same water test and countryside patches as the vector ground at that point, so the colours meet at the vector reach. **Coast (seed generator 2):** no surface triangle mixes water and land colours. A triangle whose vertices are partly water takes one side from the water test at its centroid: if water, all three vertices get the water colour; if land, its water vertices get the land colour at the centroid. The vertices that change are duplicated (more vertices, no extra triangles), so the coast and lake shores are hard edges along TIN edges, with no land-coloured spikes into the sea and no hair lines across lakes. Land classes among themselves (forest / grass / airfield, tints) still blend across a triangle as before. Every other world's terrain tiles stay without COLOR. Never empty (at least 2 surface triangles plus skirts).
- `h_min` / `h_max` (ready-tile keys): lowest / highest surface vertex.
- **Heights:** the mesh samples the same terrain function as `ground_height_at` and the vector world; between its vertices it deviates by at most the error bound above. **[1.7]** In a seed world the error bound of a sample is scaled by the lift weight `k` of section 9 "Airports" (at least 1 cm): inside an airport fence the TIN is exact to 1 cm (the levelled strips are planar), and in the shoulder it never exceeds the lowered drape lift. This costs more triangles on airport tiles only (EYVI T1 663 -> 1949, EYKA T1 1634 -> 2359 at the defaults, within `max_triangles`). The vector world's drape (section 9) is a fixed table and does not depend on the detail; the terrain mesh is sunk under the height function at every detail, so no `set_terrain_detail` value makes roads dip under it.
- **Sink [1.7]:** after the TIN is built, its vertices are lowered so that the mesh lies **on or under every lattice sample** of the tile (the grid it was built from, edges included; within f32 and projection rounding, the TIN being linear in metres and the lattice in Web Mercator: up to about 1 cm on a z10 tile): each vertex sinks by at most the largest excess of its triangles' planes over the samples in them, which is at most the TIN's error, so the mesh lies **at most twice the error bound under** the height function at the samples (the skirt is sized for that). Where a triangle's plane lies above a sample, the missing part goes to its vertices by barycentric weight (a sample next to one vertex mostly sinks that vertex), each vertex capped as above; a triangle the caps leave open lowers its vertices to the smallest common floor that closes it. A vertex none of whose triangles lies above a sample keeps its height (flat land, for example). **Seed world:** a vertex in the sea or a lake (the water rule applies there and no airport strip or shoulder touches it) never sinks, so the sea and lakes stay exactly at their level in the terrain mesh; the shore triangles that touch such a vertex can still lie up to the error bound above a land or shore sample. Inside an airport fence the TIN error is 1 cm, but a runway vertex shared with a TIN triangle that reaches into the shoulder can sink by that triangle's excess (measured at most 3 cm under the EYVI / EYKA runways, T0–T2). **Known limit:** the sink holds at the lattice samples only (about 22 m apart at z12–z14, 44 m at z11, 88 m at z10). Between them the height function can bend above the TIN: on the default relief (amplitude 450 m, 4000 random points per band) measured up to 0.19 m at T0, 0.16 m at T1, 0.35 m at T2, 1.55 m at T3 and 0.32 m at T4 (the vector drape lift is 0.125 / 0.375 / 1 / 2.5 m), at a runway end's kink up to the fence's 6 cm, and on the convex start of an airport shoulder (fence level -> relief within `seed.airport.shoulder_m`) up to 0.83 m above `ground_height_at`, where the drape lift is near 0, so the terrain mesh can show through the drawn ground in the first ~40 m outside a fence (measured up to 0.69 m at EYVI).
- Terrain output is final on first delivery (a pure function of key, profile, configure origin and detail; **[1.7]** and the seed world's files); a re-delivery happens only after `set_terrain_detail`.

## 10. Data source, cache, attribution [0.5]

- Tile source: a self-hosted PMTiles v3 archive (planetiler profile in `data/`) with layers `buildings` (keeping building `kind`), `landuse` and `roads`, zooms 13–16, fetched with HTTP range requests (rustls; no OpenSSL). Never public OSM tile servers.
- **[1.0]** Optional `buildings` attributes, each written only when the tag is present (`data/README.md`): `historic`, `man_made` (raw values), `windows` (bool: `windows=yes|no`, else `window=yes|no`), `ruins` (`ruins=yes`), `disused` (`disused=yes`), `abandoned` (any `abandoned:building`). `kind` is unchanged (raw `building`). Archives without them still work: every attribute counts as absent (a castle tagged `building=yes` + `historic=castle` then resolves through landuse). The tileset contract check (section 3.1) does not require them.
- Disk cache under `cache_dir`, raw tile bytes keyed by `z/x/y`, in one SQLite file per source URL: `{cache_dir}/tiles-{hash}.sqlite` (plus `-wal` while open; `{hash}` = 16 hex digits of the URL). LRU by bytes of tile data, capped at 300 MiB (profile `cache.cap_mb` since 0.6; `debug_stats().cache_mb` counts the same bytes). The file's pages in use are bounded too (cap + 5 % + 1 MiB), plus up to ~4 MiB of WAL between checkpoints: at the 300 MiB default the file and WAL peak at ~321 MiB, and a full cache holds about 80-87 % of the cap in tile data. It survives restarts and works offline when warm. It is wiped when the archive's header fingerprint or the cache schema version changes. Meshes are never cached, so a meshing change never serves stale geometry. The file-per-tile folders of earlier builds (`pmtiles-v{N}-{hash}/`, `pmtiles-{hash}/`) of the same source are deleted on first open; their tiles are fetched again. A corrupt file is deleted and recreated (info log); the cache is disposable and never needs user action.
- Attribution "© OpenStreetMap contributors" must be shown by the host whenever map data is visible (returned by `configure_world` since 0.6 and by `attributions()` since 0.7).
- The archive must match the tileset contract (zooms 13..16, layers `buildings`, `landuse`, `roads`); checked when it opens (section 3.1). **[0.6]**

## 11. Determinism and threading [0.5]

- Same tile → same mesh, same ground, same lights and same lit windows: everything is seeded by OSM id, with no time-based or process-random state. **[1.4]** The terrain is a pure function (seed, profile `terrain` keys, configure origin, point; integer-hash value noise in f64 with a fixed operation order), sampled directly by every job and by the cover: bit-identical on every thread and in every call order, with no cache or load state, so terrain output is final on first delivery. Pinned by golden hashes with the terrain active (`golden_tile_hashes_with_terrain`, amplitude 120 m, no flat zone; tiles and cover); the flat goldens are unchanged. **[1.5]** The terrain mesh (TIN, skirts) is pinned the same way (`golden_terrain_mesh_and_layer_cover`: two tiles per terrain band and the terrain layer's cover for fixed cameras, one with a ~2 km synthetic peak). Output order is deterministic. Pinned since 0.6 by golden hashes in `cargo test` (`simworld-core` `golden_tests`: per-tile hashes of the synthetic city for all 4 bands, positions quantized to 1 mm, colors to 8 bits, per-building output sorted by OSM id; plus the cover for fixed cameras). **[1.7]** A seed world is a pure function of its files, the profile and the key (counter-based hashes, quantized inputs, `libm` maths; no frame or floating origin in generation): pinned by `golden_seed_world_tiles` (seed tiles of the two-cities world `low-poly-map/world/two-cities/` in every band and three seed terrain tiles with COLOR). P6 adds the real-data fixture and both CPU architectures.
- The library never calls Godot APIs off the main thread; workers produce plain Rust structs and conversion to Packed arrays happens inside `poll_ready` on the calling thread.

## 11a. Lifecycle [0.7]

- **One node = one world.** Re-calling `configure` or a successful `configure_world` is a fresh start; a failed `configure_world` changes nothing. (0.5/0.6 behaviour, unchanged.)
- **Several instances in one process are allowed** (e.g. a main view plus a map viewport), each node with its own world. The library keeps no process-global state; instances share nothing (each has its own worker threads). Two instances must not use the same `cache_dir`: the second `configure_world` fails with `cache_dir in use: <cache_dir>` (section 3.1). The lock is per folder (also through a different spelling of the same path), not per tile source; a world with no disk cache (empty `cache_dir`, or the synthetic city) takes none. It is an OS file lock (`std::fs::File::try_lock`), so it also excludes other processes and is dropped by the OS if the process dies. If the folder cannot be locked for another reason (read-only volume, no lock support) a warning is logged and the world runs without the lock.
- **Teleport:** calling `configure_world` (or `configure`) again with a new origin drops all tiles (every key the host holds appears in the next `poll_unload`), resets the origin (no `origin_shifted`; `take_origin_shift` returns zero) and keeps the disk cache. The host treats it as a fresh start. The old workers are stopped **before** the new ones start: when they used a disk cache, with a bounded wait (≤ 1 s, usually a few ms) until their cache reads/writes have finished, so the new world never opens the folder while the old one still writes to it. The lock stays held across a teleport with the same `cache_dir`; with a different `cache_dir` the new folder is locked first (failure = nothing changes) and the old one released after the old workers stopped.
- **`shutdown()`** stops with the bounded wait and releases the lock; the node is inert until configured again (section 3).
- **Freeing the node** stops the workers in the background with no wait and releases the lock at once; the cache thread may still be committing its last writes and closing the file just after. A next owner that opens the same cache file in that moment gets it busy (SQLite holds it exclusively) and runs that configuration without a disk cache, with a warning; tiles then stream from the network, and the next configure opens the cache normally. Call `shutdown()` first when another node will take over the same `cache_dir` immediately.
- The cache key includes the tileset fingerprint and the cache schema version; raw bytes are cached, meshes are not, so a profile change never serves stale geometry. If meshes are ever cached, the profile hash joins the key.
